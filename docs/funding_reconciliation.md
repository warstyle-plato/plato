# Сверка бюджета, оплат, лимита и дополнительной потребности

Общий объект `own_money.reconciliation` / `funding.reconciliation` формируется
одним расчётом. Его `display_rows` читают плашки, текст и HTML сводки и
адаптер Монитора. Клиент не вычисляет дополнительную потребность заново.

Полный лимит уже включает оплаченное. В равенстве бюджета используется его
остаток: бюджет = оплачено + остаток лимита + расчётная дополнительная
потребность + явно названные несверенные части − неиспользуемая ёмкость.
Последняя нужна, когда одной главе денег не хватает, а свободный лимит другой
главы нельзя перебросить. Дефицит не присваивается остатком этого равенства:
он получается из программ отдельных глав. Разница модели и графика,
несверенные оплаты и бюджет без денежной главы сохраняются отдельно.

`matches` означает арифметическую сверку этих источников, а не приёмку
денежных документов. `primary_source_gate=BLOCKED`,
`financial_acceptance_performed=false`, `confirmed_additional=null` остаются
неизменными до отдельной закрытой финансовой проверки. Синтетические проверки
не заменяют её.

## Карта и включение АХР в график

Смешанная карта без денежных долей больше не выбирает главу большинством
строк. Сумма и помесячная программа остаются в `chapter_flow[""]` и в
`unallocated_programme`, не становятся автоматически расходами за свой счёт.
Подтверждённое ранее решение владельца для конкретной статьи сохраняется.

Наличие кода РСС 2.6 не доказывает, что график содержит все офисные АХР.
Непроверенное включение остаётся `unknown`. Неучтённый план добавляется один
раз в оба читателя программы только при явном `excluded` для точных версий,
даты и исходной листовой строки. `included` ничего повторно не добавляет.

В серверных метаданных выбранного графика допускается `admin_coverage`:

```json
{
  "basis": "reviewed_sources",
  "cut": "2026-10-31",
  "budget_sha256": "<SHA-256 проверенных байтов финансовой базы>",
  "schedule_sha256": "<SHA-256 проверенных байтов графика>",
  "items": [{"code": "2.4.1", "source_row": 15, "state": "excluded"}]
}
```

Это частный результат проверки источников, не новое поле пользовательского
upload и не допуск к выпуску. Публичный файл Excel не может сам назначить эту
запись: штатная загрузка графика её не записывает. Смена хеша, даты или строки,
дубликат решения и неподтверждённый помесячный план снимают применимость.
При оплатах главы после даты базы остаток АХР не определяется догадкой:
нужна проверенная построчная сверка платежей. Метаданные покрытия не
подтверждают кредитное покрытие и не дедуплицируют РСС/БДДС.

## По работам и месяцам

`need_breakdown.chapters` и их `months` используют ту же программу и тот же
остаток лимита главы. Превышение лимита уже оплаченным выделяется отдельно:
оно не называется будущей работой. Итоги главы и расшифровка по месяцам не
складываются друг с другом повторно.

Каталоги `model_articles` и `schedule_articles` сохраняют названия, коды,
планы, исходные строки/ячейки и помесячные показания. План или остаток статьи
не объявляется её дефицитом. Без проверенной денежной привязки её поля
`to_pay_at_cut`, `covered`, `uncovered` остаются `null`; общий дефицит не
размазывается по доле бюджета, названиям работ или числу строк.

Граница поддержанного чтения: прежний `read_schedule` не извлекает банковские
тройки справа. В проверенном репозиторном примере `Банк сен` / `Резерв сен`
не содержат года, тогда как основной план охватывает два года. Их нельзя
самостоятельно назначить на год. `coverage_columns_state` хранит это как
`not_read_by_supported_parser`, а интерфейс коротко сообщает, что покрытие
отдельных работ ещё не разобрано и не подтверждено. Это ограничение чтения,
а не утверждение, что владелец не предоставил банковские данные.

Следующий узкий reader должен находить роль, месяц и год только по явным
заголовкам/объединениям. Значение общей главы не заимствуется строкой работы;
пустая/непрочитанная ячейка не становится нулём. Нужны ссылки на точные ячейки,
проверка итогов и первичная сверка конкретной версии файла.

## Безопасный следующий шаг доступа к уже сохранённым файлам CORE

В этой среде нет подключённого read-only хранилища CORE или готового runner.
Новая загрузка документов и ключ администратора в чате не нужны.
Существующий `scripts/inspect_funding_sources.py` можно выполнить отдельно
от рабочего приложения доверенным оператором/runner:

1. Проверенный неизменяемый снимок кода и одобренный runtime с зависимостями
   подключаются только на чтение. Код из произвольного PR на CORE не запускается.
2. Подключаются только явно выбранные финансовая база, РСС, график, БДДС и
   их метаданные; без каталога ключей, общей выгрузки проектов или сети.
3. Процесс работает от непривилегированной учётной записи, с read-only root,
   временной записью только в отдельный `/tmp`; `.parsed` и исходники не меняются.
4. Preflight получает явные аргументы файлов и дату среза, описанные в
   `funding_primary_source_preflight.md`. Его код 2 / BLOCKED ожидаем и не
   заменяется на success. В публичный журнал допустим только его безопасный
   JSON с хешами и счётчиками, без денежных значений, путей и текстов исключений.
5. Денежная матрица и проверка идентичности платежей остаются в закрытом
   контуре владельца. В GitHub передаются только границы, хеши, результаты
   проверок и оставшиеся блокеры. Затем требуется независимая финансовая приёмка.

Этот документ не создаёт runner, не меняет workflow, не даёт доступа и не
выполняет production-команд.
