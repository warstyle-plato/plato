## 2. Бизнес-задача

Нужен инвестиционный модуль, который по адресу потенциального девелоперского проекта автоматически:

1. определяет координаты адреса;
2. находит актуальные жилые новостройки / первичные конкурирующие проекты в радиусе 1/3/5 км;
3. исключает вторичку, офисы, апарт-офисные объекты, старые нерелевантные здания и проекты из других городов;
4. корректно дедуплицирует один ЖК, найденный через несколько источников/вариантов названия;
5. по каждому проекту показывает текущую цену предложения за м², диапазон, число наблюдений, желательно экспозицию / количество лотов;
6. хранит источник и дату каждого показателя;
7. считает устойчивую рыночную рекомендацию цены;
8. позволяет кнопкой передать рекомендованную цену в поле `Цена квартир` основной финансовой модели и запустить перерасчёт.

Это не каталог недвижимости. Цель — получить проверяемый входной параметр для инвестиционной модели.

## 4. Что уже исправлялось и почему

1. Старый приватный endpoint Наш.Дом.РФ давал 403 — исключён из архитектуры.
2. Парсер цен изначально понимал только `598 500 ₽/м²`; добавлена поддержка `598,5 тыс. ₽/м²` и расчёта `цена квартиры / площадь`.
3. Добавлены ЦИАН, Домклик, Яндекс Недвижимость как источники asking-price через поисковый индекс.
4. Наш.Дом.РФ перестал быть единственным discovery-источником и hard gate.
5. Официальная средняя Наш.Дом.РФ больше не должна подменять текущий рынок предложения: asking-price — базовый параметр рекомендации; официальный показатель — контроль/fallback.
6. Добавлена защита от явного несовпадения региона (пример: `СВОЙ` из Хабаровска не должен подтверждаться для Москвы).
7. Добавлялась фильтрация офисов/вторички/старых нерелевантных объектов.
8. Добавлялась кнопка применения сводной цены в `Цена квартир`.
9. UI был очищен от части технических ID/поисковых ссылок.

## 5. Текущий live-результат — НЕПРИЕМЛЕМ

На контрольном адресе `Москва, Саввинская набережная, 25` preview выдаёт очевидный мусор. Зафиксированные примеры:

- `Сидней Сити (Sidney City)` — 0 км;
- `Москвы. Рейтинг застройщиков Дубая. Адрес офиса` — 0 км;
- `Cult (Культ) - купить квартиру` — 0 км;
- `Тургенев - купить квартиру` — 0 км;
- `Мод` — 0 км;
- несколько дублей / вариантов `Savvin River Residence`;
- подозрительное наследование адреса subject-объекта кандидатами, из-за чего возникает 0 км;
- цена извлекается из неоднородных сниппетов и иногда не привязана надёжно к entity;
- экспозиция почти отсутствует;
- ссылки часто ведут на поисковые/технические страницы, а не на каноническую страницу проекта.

То есть проблема сейчас не косметическая. Entity extraction + entity resolution + geocoding fundamentally unreliable.

## 6. Что требуется от Claude

Не латать очередной regex поверх текущего результата. Сначала провести независимую forensic-ревизию всей цепочки:

`search documents -> candidate extraction -> canonical entity -> address resolution -> geocoding -> distance -> source matching -> price/inventory enrichment -> recommendation -> UI`.

Нужно найти первопричины каждого класса ошибки и предложить/реализовать архитектуру, в которой эти ошибки структурно невозможны или явно quarantine-ятся.

### Обязательные вопросы для ревизии

1. Почему кандидаты вроде `Рейтинг застройщиков Дубая. Адрес офиса` вообще проходят extractor?
2. Почему разные unrelated candidates получают координаты subject address и становятся `0 km`?
3. Почему один проект появляется несколькими entities?
4. Почему price enrichment может использовать наблюдение, которое относится к другому проекту/очереди?
5. Почему catalog-first search пока не извлекает список проектов из каталога как отдельные entities, а часто берёт title всей страницы?
6. Нужен ли отдельный deterministic parser для известных aggregator URL/path типов вместо generic title parsing?
7. Как лучше строить entity resolution: canonical key по `(normalized_name, developer, address/coords)` + aliases?
8. Как получать exposure/inventory воспроизводимо и отдельно маркировать качество данных?

## 7. Предпочтительная архитектура

Claude может её изменить, но обязан объяснить причины.

### Discovery

Использовать несколько независимых каналов, а не один generic Yandex query:

- районные/географические каталоги ЦИАН;
- районные/географические страницы Яндекс Недвижимости;
- Домклик;
- официальные сайты девелоперов;
- Наш.Дом.РФ как официальный источник проекта/строительства;
- general Yandex Search только как fallback/discovery glue.

Для каталожных страниц желательно извлекать отдельные project records, а не принимать `<title>` каталога за название ЖК.

### Entity resolution

Перед геокодированием проект должен иметь минимум:

- `raw_name`;
- `canonical_name`;
- `source_domain`;
- `source_url`;
- `developer` при наличии;
- `address_hint` при наличии;
- `candidate_type` (`project`, `listing`, `article`, `catalog`, `developer_page`, etc.);
- `extraction_confidence`.

`article`, `catalog`, `listing`, `office`, `secondary` не должны становиться project entity без явного извлечённого project child.

### География

Запрещено геокодировать generic candidate путем подстановки subject address.

Если у кандидата нет собственного валидного адреса/координат:
- сначала искать адрес проекта;
- если адрес не найден уверенно — `geo_unresolved`, а не `0 km`;
- такой объект не должен участвовать в price recommendation.

### Дедупликация

Один ЖК из разных источников должен схлопываться в одну entity.
Предпочтительно учитывать:
- нормализованное название/aliases;
- адрес/координаты;
- developer;
- official object ids;
- близость координат.

### Pricing

Нужно разделять:
- developer/primary asking price;
- aggregator asking price;
- official Наш.Дом.РФ average;
- secondary/resale — не смешивать с primary.

Хранить минимум:
- `price_per_sqm_min`;
- `price_per_sqm_median`;
- `price_per_sqm_avg`;
- `sample_count`;
- `source`;
- `observed_at`;
- `quality/confidence`.

Наблюдение цены не использовать, если entity-match не подтверждён.

### Exposure

Нужно добавить минимум:
- `inventory_developer`;
- `inventory_total_market`;
- `inventory_source`;
- `inventory_observed_at`;
- `inventory_quality`.

Если точное число получить нельзя, лучше `null + quality=unknown`, чем выдумывать/переиспользовать число из нерелевантного сниппета.

### Recommendation

Текущий `recommendation.py` можно переиспользовать, но только после очищения entity-set.
Рекомендация не должна рассчитываться по discovery-only / geo-unresolved / price-unverified entities.

Желательно учитывать:
- distance;
- класс;
- status/stage;
- срок ввода;
- качество price evidence;
- количество независимых источников.

## 9. UX после исправления данных

Текущие большие карточки выглядят плохо и масштабируются плохо.
Нужен компактный инвестиционный экран:

Верхние KPI:
- найдено проектов;
- валидных аналогов;
- медиана ₽/м²;
- рекомендованная цена;
- суммарная экспозиция;
- confidence.

Основной вид — таблица:
`ЖК | расстояние | класс | сдача | цена ₽/м² | экспозиция | источники | качество`.

Отдельно карта.
Подробности/источники — раскрываемая строка/карточка.
Не показывать внутренние ID и технический search noise.

Кнопка:
`Применить рекомендованную цену в модель`.
Она должна записывать цену в поле `Цена квартир` основной модели в `тыс. ₽/м²` и запускать пересчёт.
