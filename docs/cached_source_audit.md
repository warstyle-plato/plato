# Закрытая выгрузка сохранённых источников

Два служебных POST позволяют контролю проверить уже сохранённые данные без
обычных GET, которые могут запускать обновление. Они не меняют расчёты,
расписание, финансовый результат или связи источников. Публичной страницы нет.

## Доступ и транспорт

`POST /monitor/audit/sources` использует существующий строгий
`_require_admin_key(..., "Монитор проекта", ...)`: вход Telegram, команда,
демо и ключ рынка доступа не дают. `POST /auctions/krt/audit/cached` использует
существующую owner admission `_require_admin` и дополнительно закрывается при
отсутствии настроенного владельца. Ключ передаётся в JSON-поле `key`; КРТ также
принимает `X-Developaid-Admin-Key`. Входные URL не содержат ключей.

Оба POST проходят собственный допуск до импорта сборщика, определения корня и
чтения источников. Исключение из market middleware касается только этих двух
POST и не даёт им доступа без своего допуска. Ошибки и результаты имеют
`Cache-Control: private, no-store`; ответ ошибки содержит фиксированный код,
без provider exception, пути, ключей или исходного документа. Размер входного
JSON ограничен 16 KiB, лишние поля, дубли ключей и нечисловые JSON-константы
отвергаются. Имена файлов, корень, URL, offset и список полей клиент не задаёт.

Выдача содержит частные данные владельца. Контроль забирает её только по HTTPS
в закрытый зашифрованный артефакт с заранее проверенным получателем. JSON,
base64 и ключи не печатаются в Actions/chat/public artifacts. Шифрование
артефакта выполняет вызывающий закрытый сборщик; API не публикует ссылки.

## Финансовые первоисточники

JSON содержит только `key`, необязательный `session`,
`purpose: "finance_sources_v1"`, логическое имя `project` и явную дату `cut`
в формате `YYYY-MM-DD`, не позже текущей даты UTC.

Корень берётся из существующего `developaid_monitor._SNAPSHOT_DIR`.
Применяется существующий чистый `_slug` и один безопасный переход из
`.aliases.json`. Создающий каталоги `_project_dir`, кеш aliases, финансовые
парсеры и хранилища не вызываются. Неизвестный проект не создаётся.

| Слот | Единственный разрешённый источник |
| --- | --- |
| `finance` | `<проект>/baseline/finance.xlsx` |
| `finance_meta` | `<проект>/baseline/finance_meta.json` |
| `bank_rss` | `<проект>/estimate/YYYY-MM-DD.xlsx`, самая поздняя корректная календарная дата не позже `cut` |
| `bank_rss_meta` | JSON с той же датой, что выбранная РСС |

XLSX выдаются исходными байтами в `content_base64`, без openpyxl и кешей.
Метаданные JSON проецируются только на существующие поля имени файла, дат и
размера; неизвестные дополнительные поля не выдаются. Для каждого прочитанного
источника указаны SHA-256 исходных байтов, размер, inode и mtime. SHA метаданных
относится к оригинальному JSON, а не к его сокращённой проекции.

ФМ сверяется с заранее принятым SHA-256
`4732693f3f2b3c368a2af9a7975716844fe010e9de6abb6efcc48204fe7f9bf9`.
Несовпадение сохраняет наблюдаемые байты и явный gap. Оно не становится
финансовой приёмкой. Текущая ФМ с датой позже `cut`, неизвестная дата,
отсутствующие метаданные и несовпадение даты/размера РСС названы отдельно.
Дата загрузки, mtime и имя файла не считаются датой подтверждения оплат.
Платежи находятся в самой РСС; БДДС, график финансирования, `.parsed` и
журналы распределения не читаются и не являются условием этой выдачи.

## Сохранённое состояние КРТ

JSON содержит только `key`, необязательный `session` и один `purpose`:

* `krt_cached_metadata_v1`: состав, статусы и их история, даты, версии,
  полнота обхода, SHA и наличие модели/рейтинга без их содержимого;
* `krt_cached_replay_v1`: та же информация плюс сохранённые структурированные
  поля рейтинга/модели. Числа и неизвестные значения не заменяются.

Корень определяется по уже созданным native registry/ranking stores. Разные
корни дают отказ. Конструкторы, GET-каталоги, `refresh`, screening/model/rating
функции и загрузчики документов не вызываются.

Разрешены только `catalogue.json`, `decisions.json`, `ranking.json`,
`schedule.json`, необязательные `first_seen.json`, `watch_seen.json`,
`rating_settings.json` и JSON из фиксированных `reports`, `market-reports`,
`decision_tep`, `decision_requirements`. Имена ограничены безопасным slug.
Auth/config/credentials-файлы и любые другие каталоги недоступны.

Проекция сохраняет поля идентичности каталога и документов, район/округ,
статусы, `last_known_status_kind`, конфликт, опубликованность, основные ТЭП и
даты. Оригинальные URL документов допускаются только на `mos.ru` и его
поддоменах без userinfo/query/fragment. Тела PDF и рыночных ответов не выдаются.
Replay добавляет native `investment_rating` и версионные/числовые поля строки,
а из `screening` — `model_inputs`, `metrics`, `tep_ratios`, `requirements`,
`renovation`, `programme`, `market`, `phasing`, `absorption`, `entry_capacity`,
`at_asking_price`, `available`, `preliminary`, `traffic_light`. Вложенные ключи
prompt/auth/credential и повествовательные тела удаляются; секретные маркеры
приводят к закрытому отказу. Сборщик не генерирует отсутствующий модельный
ответ и не объявляет такой replay завершённой проверкой.

Ранние проекты берутся при последующем offline replay из точного исходного
runtime-коммита `auction_search/krt_early_projects.py`, а не придумываются по
рейтингу. Это отдельный явно названный gap выгрузки. Процессные refresh-флаги
наблюдаются только у обслужившего запрос worker; второй worker неизвестен.

## Ограничения и целостность

Сборщик — stdlib-модуль без импорта приложения, сети и записей. Корень и все
компоненты открываются через directory FD с `O_NOFOLLOW`; принимаются только
обычные файлы с одной жёсткой ссылкой. FIFO, симлинк, выход из namespace и
подмена каталога закрывают выдачу. После чтения повторяются состав файлов,
SHA/размер/inode/mtime и привязка aliases. Изменение даёт `snapshot_changed`,
а не смешанный результат. Будущая РСС не меняет выбор исторического среза.

Лимиты: 4000 файлов/элементов обхода; 16 MiB на файл; 256 MiB суммарного чтения
КРТ с повторным проходом; 16 MiB исходных XLSX финансов на оба слота вместе;
64 KiB на JSON метаданных/aliases; 23 MiB на JSON-ответ. Лимиты исходных
финансовых файлов проверяются по FD до чтения байтов. Превышение — явный
`source_size_limit`/413, не сообщение «данные не предоставлены».

В ответе всегда разделены `coherent` и приёмка. Согласованный снимок не
доказывает полноту проекта, свежесть всех расчётов или правильность денег.
`evidence_complete`, `production_acceptance`/`financial_acceptance` остаются
ложными; `gaps` и `null` сохраняют отсутствие доказательств.

## Использование для приёмки #1050

Исторический целевой срок — 08.11.2026 03:00 МСК, то есть 00:00 UTC.
Сохранённые `schedule` и хеши описывают только реально существующие данные.
Если immutable cohort/before-after не были сохранены, этот пробел нельзя
заменить зелёным synthetic weekly test.

После закрытого capture контроль отдельно проверяет candidate replay на полном
реальном cached cohort: все внешние/model clients заменены recorder с отказом
выхода в сеть, outputs не синтезируются; проверяются посещения, исключения и
before/after сохранённых моделей и баллов. Это offline replay, а не реальный
воскресный прод-проход. Минимальный immutable weekly trace для следующего
штатного прохода и последующее наблюдение относятся к самой задаче #1050;
эти два read-only POST его не запускают и не подменяют.
