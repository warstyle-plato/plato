# Проверка сохранённых источников финансирования

`scripts/inspect_funding_sources.py` — локальная проверка файлов, уже
сохранённых в Monitor. Это подготовка к закрытой финансовой сверке #999,
а не новый API, выгрузка первички или допуск к выпуску.

Запускать из отдельной проверенной рабочей копии кода, с доступом на чтение
к существующим файлам сервера. Не заменять рабочий код приложения ради
диагностики. Доступ к файлам сервера этой командой не предоставляется.
Ключ администратора и повторная загрузка в Monitor не нужны.

Пример с условными локальными путями:

```bash
python scripts/inspect_funding_sources.py --cut 2026-10-31 \
  --finance /readonly/baseline/finance.xlsx \
  --finance-meta /readonly/baseline/finance_meta.json \
  --rss /readonly/estimate/2026-10-30.xlsx \
  --rss-meta /readonly/estimate/2026-10-30.json \
  --schedule /readonly/funding_schedule/2026-08-13.xlsx \
  --schedule-meta /readonly/funding_schedule/2026-08-13.json \
  --bdds /readonly/budget/month.xlsx
```

Файлы выбираются явно: команда не угадывает проект и действующую версию.
Для нескольких БДДС повторить `--bdds`; если нужны их метаданные,
передать столько же `--bdds-meta`, в том же порядке. Отсутствующий аргумент
даёт `not_supplied`, недоступный или нечитаемый файл — `unreadable`.
`state: read` означает чтение книги; результат профильного парсера отдельно
указан в `parsed`. Каждый файл ограничен 32 МиБ.
Причина отказа передаётся фиксированным `error`: файл не найден,
доступ запрещён, превышен размер, ошибка чтения файла/книги или отказ
профильного парсера. Исходный текст исключения не передаётся.

Вывод — JSON с датой среза, SHA-256 прочитанных книг, датами `taken_at`
из явно переданных метаданных, счётчиками и признаками. Имена и пути,
суммы, тексты ячеек, идентификаторы платежей и сообщения ошибок в него
не включаются. Файлы источников и `.parsed` не изменяются: существующие
парсеры получают потоки в памяти, обходя дисковый кэш и его pickle-файлы.
Команда не обращается к сети. JSON не содержит первичные документы.

Финмодель проверяется существующим расчётом АХР: листовые строки без
налогов, известность сохранённых денежных ячеек, число однозначных
соответствий главам 2/3 и вне глав 1–3, смешанные и отсутствующие
соответствия, тождества сумм. Счётчики `admin_dictionary_*` описывают
справочник; `admin_verified_money_leaf_count` — строки с проверенными
месячными денежными источниками. Справочник не становится денежной картой.
Эти признаки относятся к результату парсера,
не являются независимой денежной приёмкой. Количества строк не превращаются
в денежные доли. Пустой кэш формулы остаётся неизвестным.

Первые 20 строк **каждого** листа каждой книги просматриваются на точные
заголовки `ID платежа`, `Идентификатор платежа`, `Payment ID`.
`payment_id_header_candidates` — только число найденных заголовков.
Ноль не доказывает отсутствия идентификаторов: возможны другие названия,
другая строка шапки или составной ключ, требующий проверки. Наличие
заголовка не подтверждает единство идентификаторов между РСС и БДДС.
Совпадение сумм, дат, договора или номера строки не используется как
доказательство одинаковых платежей.

Дата файла, mtime, свойства Excel и время загрузки не подставляются вместо
даты версии финансовой базы. Даже известный `taken_at` сам по себе не
доказывает утверждение версии на 31.10.2026. Наличие месяца БДДС не
подтверждает полноту факта на конец месяца. Прочитанный график не доказывает
включение АХР или кредитное покрытие.

`primary_source_gate` всегда `BLOCKED`, финансовая приёмка — `false`,
непроверенные покрытия, идентичность платежей и дата базы — `null`.
Код завершения **2**, в том числе при успешном чтении всех файлов,
намеренно не позволяет объявить эту диагностику зелёной финансовой приёмкой.
Это ожидаемый результат, а не повод повторять загрузку или менять источники.

Следующий шаг выполняется в закрытом контуре: подтвердить действующие
версии и даты, проверить денежную карту листовых строк, связь с позициями
графика и условиями банка, затем сверить платежи РСС/БДДС по проверенным
идентификаторам до среза (в том числе после даты книги). Нужны числовые
доказательства отсутствия потери и двойного счёта, а затем независимая
финансовая рецензия точного SHA. Диагностика этого не выполняет и деньги
продуктового расчёта не меняет.
