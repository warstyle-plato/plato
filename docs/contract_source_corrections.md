# Исправление источников договора

Подтверждение номера и выбор исправленных источников — разные операции.
Прежний `/monitor/contracts/identity/confirm` по-прежнему принимает ровно две
карточки с одинаковыми сторонами и датой. Он не становится разрешением
нормализовать юридические имена или выбирать суммы по сходству.

## Предварительный просмотр и запись

Новые операции того же административного job-профиля `contract-identity`:

- `correction-inventory`: от двух до восьми явно выбранных исходных ID;
- `correction-preview`: источник исправленных реквизитов, токен выполнения,
  токен полной цены либо явный `null`, ID существующей карточки документов;
- `correct-sources`: те же выборы, SHA инвентаризации и просмотра, все source
  tokens, ожидаемые revision/head и основание;
- прежние `resolve`, `revoke`, `result` понимают новый вид решения.

Клиент не передаёт суммы, количества, свободные юридические реквизиты,
таблицы aliases, actor, серверное время или пути. Токены выпускает сервер из
квалифицированного исходного результата. Просмотр показывает прежние и
исправленные реквизиты, выбранные роли и последствия. Подтверждение повторяет
проверку под namespace, identity и существующими native locks; запись — одно
событие `correct_sources` прежнего append-only журнала. Отмена добавляет событие.
Пересекающиеся группы, цепочки, stale CAS и неподтверждённые версии отвергаются.

Политика `follow_selected_native_v1` закрепляет выбранную карточку выполнения
и владельца документов. Новая неизменяемая КС с точной канонической
идентичностью проходит прежние правила периодов и редакций. Новый
квалифицированный договор/ДС в той же карточке документов проходит native
правила цены. Повтор прежнего файла в другом архиве не становится новым
выполнением. Новые неподтверждённые raw-ID и изменённые ранее проверенные
исходники не получают принадлежность автоматически.

Не связанная с группой новая загрузка не возвращает отвергнутые исходные
варианты в список. Свежесть проверяется по группе и по роли. При конфликте
показываются прежние известные выбранные показатели с происхождением и
причиной проверки. Безопасная роль остаётся читаемой. Неизвестное не становится
нулём. Полная цена и выполнение могут быть известны отдельно при неизвестных
общем проценте и остатке; отдельная финансовая приёмка не является блокировкой.

## Чтение и изменения

В обычном списке остаётся одна исправленная карточка. Исходные карточки,
документы, снятия, сроки и выборы остаются по прежним адресам в свёрнутой
истории. До даты выбранного исправленного источника срез сохраняет прежний
состав и сообщает, с какой даты доступны исправленные источники.

Большие исходные деревья не вкладываются повторно в каждую строку:
`raw_source_rows` содержит только участвующие исходные карточки, а активная
строка ссылается на выполнение. `ownership.raw_rows` восстанавливает прежний
порядок; `correction.materialize` даёт временный вид для native потребителя.
Остальные карточки передаются один раз. Сохраняется штатный chunked transport.
Сборка ограничена восемью группами, прежними пределами архивов/байтов и общим
пределом метаданных; проверка ZIP разделяется между группами одного чтения.

Операционная карточка запрашивается явно с `view=operational`, correction ID
и read guard; прежние raw-запросы сохраняют значение. Для изменения клиент
передаёт действительный выбранный raw-ID владельца документов вместе с
logical ID и тем же guard. Сервер проверяет их под блокировками до native
записи и обновляет guard после собственной записи. Заголовок и обычный путь
загрузки для пользователя остаются заголовком исправленного договора.

ГПР и план-факт считаются штатным consumer из выбранных КС и выбранной
карточки документов; прежний готовый контроль другого raw-ID не копируется.
Приоритет КС-2, fallback КС-6а, редакции ставок, объёмов и сохранённые выборы
не меняются. Связи ежедневных сообщений и платежей не переносятся по alias.
Excel получает тот же сохранённый DTO сравнения; revision включает роли и
read guard, а текущая выгрузка отвергает изменившиеся источники.

Новый формат события должен быть прочитан всеми воркерами до первой записи.
Откат приложения требует decoder, понимающего `correct_sources`; отмена не
удаляет событие и не делает старый decoder совместимым. Реальные исходники,
source pins, решения и предметные readback receipts остаются частными.
