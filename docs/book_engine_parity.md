# Книга Excel ↔ движок: сверка и «ок» проверяющего

Участок проверяющего «Книга ↔ движок»: книга проекта считает то же, что движок.
Расхождение методики ловит автоматическая сверка — до того, как его увидит владелец.

## Что сверяется

`scripts/book_engine_parity.py` собирает книгу каждого эталона, считает её
формулы `xlsx_eval` (не LibreOffice) и сравнивает с авторитетным расчётом движка.

| Эталон | Книга | Что это |
|---|---|---|
| `default` | v4 | Жильё одной очередью |
| `nagatino_phased` | v4 | Жильё очередями, ТЦ в четвёртой |
| `mixed_osz_parking` | v4 | Смешанный: жильё и офис ОСЗ с гаражом |
| `retail_sports` | v4 | Смешанный: жильё, ТЦ и ФОК |
| `office_ddu` | нежилая | Офис по ДДУ |
| `office_direct` | нежилая | Офис без ДДУ, продажа блоками |
| `office_rent` | нежилая | Офис без ДДУ, аренда с выходом |
| `nonres_retail_sports_ddu` | нежилая | ТЦ и ФОК по ДДУ |
| `nonres_parking_ddu` | нежилая | Наземный паркинг по ДДУ |

Жилая книга v4 (и смешанный проект):

- строки ОТЧЕТ: выручка, CAPEX, коммерческие, EBITDA, финансирование, прибыль
  до налога, налог, чистая прибыль, маржа, IRR и NPV капитала, пик долга и эскроу,
  LLCR, непогашенный долг;
- по годам (лист CF): выручка по договорам, раскрытие и остаток эскроу, расходы
  проекта, налог начисленный и уплаченный, проценты, выборка и погашение БРИДЖа и
  ПФ, долг на конец года, поток собственника, проектный поток до финансирования;
- CAPEX по главам (лист CAPEX, сумма очередей) против сметы движка;
- NPV и IRR проекта — функцией движка (`monthly_npv`, `monthly_irr`) из потока книги;
- пик собственных денег — худший накопленный поток собственника книги против
  `owner_cash_peak` движка.

Книга нежилого проекта (`office_workbook`) — каждая строка её листа «ПРОВЕРКИ»:
итоги, смета, ПФ, налог и деньги собственника по годам, NPV, IRR, пик, объекты.
Вердикт строки — формулой самой книги.

Допуск: 0,01% числа, не меньше 1 тыс. ₽; у долей — 1e-6.

## Где запускается

- Workflow «Книга ↔ движок» (`.github/workflows/book-engine-parity.yml`):
  - на PR, который трогает `engine/economics.py`, `engine/financing.py`,
    `engine/reports.py`, `engine/xlsx_book_v4*.py`, `office_workbook.py`,
    `xlsx_eval.py`, эталоны (`tests/golden/**`, `scripts/golden_snapshot.py`)
    или саму сверку;
  - каждую ночь на main; красная ночь открывает задачу (issue) «Ночная сверка
    «Книга ↔ движок»: расхождения на main», зелёная — закрывает её.
- Первый шаг прогона — подделка (`--tamper`): испорченная формула резерва в
  книге v4 и выручки в нежилой книге обязаны дать расхождение. Не дали — прогон
  красный: сверка, которая не ловит подделку, ничего не доказывает.
- В общем наборе — `tests/test_book_engine_parity.py`: охват видов проекта,
  подделка ловится, известные расхождения реальны.

Руками: `python3 scripts/book_engine_parity.py [--only имя …] [--tamper]`.
Падение пишет строку: «проект X, строка Y: книга A, движок B, разница C».

## Известные расхождения

`KNOWN_GAPS` в скрипте — только расхождения, по которым владелец уже решил, а
PR ещё не слит. Они печатаются отдельно и прогон не валят. Тест требует, чтобы
каждое из них ещё было: после слияния PR запись снимается в том же или
следующем PR.

Сейчас список пуст: расхождение по проектному потоку и NPV/IRR проекта закрыто
#892 (214-ФЗ: выручка по ДДУ входит в поток проекта раскрытием эскроу — и в
книге, и в движке).

## Как проверяющий даёт «ок» перед слиянием

PR в зоне проверяющего — любой, который запускает workflow «Книга ↔ движок»
(список путей выше).

1. Сессия контроля очерёдности присылает номер PR или проверяющий видит его сам.
2. Проверяющий смотрит прогон «Книга ↔ движок» на **последнем** коммите PR:
   - шаг «Подделка ловится» зелёный;
   - шаг «Сверка книги с движком» зелёный: в таблице прогона нет расхождений;
   - раздел «Известные расхождения» содержит только записи `KNOWN_GAPS`.
3. Если PR меняет методику (формулу движка или книги), проверяющий дополнительно
   сверяет, что правка сделана в обеих реализациях, а переписанная формула
   шаблона названа в `V4_REWRITTEN_FORMULA_ROWS`.
4. Если PR сливает решение из `KNOWN_GAPS`, запись снята в этом же PR (иначе
   `test_the_housing_book_agrees_and_its_known_gaps_are_real` красный).
5. Итог — одно сообщение сессии контроля очерёдности:
   - «ок: PR #N, книга ↔ движок, прогон <ссылка>, коммит <sha>» — можно ставить
     в очередь;
   - или «не ок: PR #N» со строками расхождений и тем, кто чинит: мелкое и
     очевидное — исполнитель PR; вопрос методики (неясно, кто прав) — владельцу
     через вопрос с вариантами.
6. «Ок» относится к коммиту. Новый push в PR снимает «ок» — нужен новый прогон.

Красный ночной прогон на main — забота проверяющего: разбор, исправление в
отдельном PR или вопрос методики владельцу.
