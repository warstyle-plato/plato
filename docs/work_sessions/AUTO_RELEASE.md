# Автоматический выпуск принятых задач

Действует постоянное указание владельца: завершённая порученная задача после
независимой приёмки точного HEAD и зелёного CI выпускается без повторного
согласования. Чат с владельцем — источник поручения для контроля. Очередь
сама не интерпретирует произвольные или архивные сообщения: она использует
машинную аттестацию контроля. PR без такой аттестации пропускается.

## Кто выдаёт допуск

Контроль сверяет точный source HEAD, результаты независимых стражей и область
поручения владельца. До завершения задачи контроль обязан **своей учётной
записью** запустить `release-approval.yml` на main с номером PR, полным source
SHA и решением `approve`. Например, после сохранения принятого SHA в
`accepted_head`:

```sh
gh workflow run release-approval.yml --ref main \
  -f pr=1234 -f head="$accepted_head" -f decision=approve
```

Если независимая приёмка закончена раньше CI, допуск можно поставить сразу:
очередь дождётся полного зелёного результата. Повторный вопрос владельцу для
уже порученного выпуска не нужен.

Сервер GitHub сохраняет неизменяемый `display_title` запуска:

```text
release-control pr=1234 head=<40 символов source SHA> decision=approve reviewed
```

Очередь проверяет canonical workflow_id/path, event `workflow_dispatch`,
head_branch `main`, repository/head_repository и точный формат заголовка.
Допуск даёт только completed/success run. Обе native identity — `actor` и
`triggering_actor` — должны быть разрешёнными людьми (`type=User`). По
умолчанию разрешён владелец репозитория.
Для организации или отдельного контроля задают repository variable
`RELEASE_CONTROL_ACTORS` — список разрешённых логинов через запятую, заменяющий
умолчание. Bot-аккаунты и логины `[bot]` не принимаются, включая собственный
`GITHUB_TOKEN` очереди. Поэтому dispatch approval-workflow ботом не создаёт
самодопуска. Персональный токен workflow не получает.

Producer работает без checkout с правами только contents/actions read.
Он читает общий `scripts/auto_release.py` через Contents API ровно на
`GITHUB_SHA` своего main-workflow, а не на переданном source SHA PR, и
исполняет read-only validator. Этот же validator используется очередью и
consumer. GitHub-записей кроме результата самого workflow producer не создаёт.

`reviewed` — аттестация контроля, что независимый рецензент проверил именно
этот HEAD; native run доказывает, кто и для какого SHA её оставил, а не
заменяет саму экспертизу. Автор не принимает свой патч. Частные документы,
финансовые суммы и материалы стражей не помещают во inputs/заголовок/логи.
Обычный GitHub approval без этого допуска не запускает выпуск.

Для отзыва контроль запускает тот же workflow с теми же PR/source SHA и
`decision=revoke`. Решения людей упорядочены по исходному immutable run.id,
а не по времени retry. Более новый pending/failed run или revoke блокирует
старый success approve. Рерун старого approve после нового revoke не
восстанавливает допуск; нужен новый explicit approve-dispatch с новым id.
Решения сохраняют в истории, отзыв оформляют новой записью. Выпуск соседнего
PR не отзывает приёмку того же source HEAD; новый source push требует новой
приёмки. Старый канал native `control/release-approved` полностью выведен из
политики: он не разрешает и не отзывает выпуск.

## Что проверяет очередь

Workflow `auto-release.yml` работает каждые пять минут и после завершения
полного CI/проверки версии/контрольного решения. GitHub может задержать cron. Исполняются только
workflow и Python из `main`; PR-код, артефакты и внешние скрипты очередь не
загружает и не запускает. Права: contents/pr/checks read, statuses write для
одноразового intent, actions write для dispatch. Публичные ответы API и
ошибки не печатаются целиком.

Контроль также может вызвать `auto-release.yml` вручную на main для проверки
работы очереди. Это не создаёт допуск: без человеческого approve-run все PR
будут пропущены с указанной причиной. Schedule/workflow_run остаются включены.

Перед выпуском заново читаются PR, текущий `main`, статусы, checks, reviews и
workflow runs. PR должен быть открытым, не draft, из этого же репозитория,
на `main`, с `mergeable=true` и `mergeable_state=clean`. Последний существенный
review каждого рецензента не должен быть `CHANGES_REQUESTED`; `COMMENTED`
не отменяет прежний запрос изменений. Решения группируются по native user.id
или известному логину; неизвестная identity блокирует выпуск, поэтому
неизвестный approval/dismissed не снимает чужой запрос изменений.
Комментарии свободным текстом не
трактуются как разрешение или отзыв: новые блокеры контроль отражает новым
revoke-run или формальным request changes.

Все опубликованные актуальные checks и остальные commit statuses должны
успешно завершиться; отсутствие, pending, failure, cancelled и neutral
не дают выпуска. Только два необязательных preview-check — «Сборка preview-образа»
и «Preview-образ готов» — могут иметь completed/skipped, когда preview не нужен.
Skipped у любой другой проверки, включая доли, rollup и version, блокирует выпуск.
Обязательны `Полный набор` и `version`, последние успешные
PR-прогоны `tests-on-pr.yml`/`version-guard.yml` на том же source HEAD и все их
успешные jobs. Полный CI включает каждую долю из матрицы **доверенного main**,
а не только зелёный rollup с отсутствующими долями. Чужой PR или более старый
успешный прогон не подменяет новый pending/failed прогон. Любой активный
PR-прогон exact source HEAD, включая Monitor/security/preview, блокирует
выпуск ещё до появления check runs. Повтор старого run сохраняет id, поэтому
порядок завершённых вердиктов определяется `run_started_at` актуальной попытки,
а не величиной id или временем завершения. Старый долгий success не перекрывает
более поздний failed attempt. Без `run_started_at` выпуск блокируется: поля
`updated_at`/`created_at` не заменяют известное начало попытки. Изменение защиты
ветки в `behind`/`blocked` также блокирует очередь.

Ранее проверенная база CI может отличаться от сегодняшнего main, как в
штатном ручном выпуске. Queue снимает свежий `expected_base` непосредственно
перед dispatch; `pull.base.sha` может быть старым снимком и не считается
авторитетным current main. Авторитетны GET git/ref и origin/main после fetch.

В REST `run.head_sha` сохраняет проверенный source SHA, а
`run.pull_requests[].head.sha` отражает текущий HEAD связанного PR. После
штатного VERSION push эта association может уже показывать issued SHA.
Gate сохраняет строгое совпадение immutable `run.head_sha` с принятым source,
номера PR и репозитория; association.head допускает source либо отдельно
зафиксированный фактический issued HEAD. До dispatch они совпадают. Чужой PR,
репозиторий или третья голова не проходят проверку.

## Один SHA — одна автоматическая попытка

У очереди один сериализованный job. Любой queued/running/waiting/pending/
requested прогон `release-merge.yml` останавливает следующий выпуск.
Перед dispatch очередь создаёт на source SHA постоянный native status
`control/release-dispatched`, state `success`, со ссылкой на свой run.
**Success здесь означает запись одноразового intent, не успешный деплой.**
Любой существующий статус этого контекста запрещает повторную автоматическую
попытку этого SHA независимо от результата release. Статус не имеет срока
хранения артефакта; очередь его не очищает и не создаёт approval.

После записи intent все gate-проверки повторяются. Только затем выполняется
POST dispatch **существующего `release-merge.yml` на main**, с `pr`,
`expected_head` и свежим `expected_base`; прямого merge API у очереди нет.
Если main/head/допуск изменились, API не ответил, процесс упал или выпуск
завершился ошибкой, intent остаётся. Бесконечного автоматического retry нет.
Контроль выясняет результат по ссылке run и истории release. Явный повтор
возможен штатным ручным release workflow после повторной сверки либо новой
порученной ревизией с новым HEAD и допуском; новый approve-run на том
же SHA недостаточно, чтобы стереть старый intent.

## Защита потребителя

Дополнительные inputs `expected_head`/`expected_base` старого release workflow
необязательны: прежние ручные вызовы сохраняют поведение. Очередь передаёт оба.
Потребитель проверяет live source HEAD, main через API и origin refs после
fetch, включая второй fetch внутри `_set_version`. При изменении main
автоматическая попытка останавливается, а не пересчитывается бесконечно.
Canonical gate из `auto_release.py` загружается из trusted main один раз и
перечитывает допуск, reviews и CI принятого source SHA до выдачи версии и
непосредственно перед merge. Отзыв допуска, новый request changes или
pending/failed rerun после dispatch останавливают consumer. Собственный
active release run исключается из проверки конкурентов.
Policy module, клиент, разрешённые actors и неизменяемая матрица обязательных
jobs сохраняются до checkout. Финальный gate не читает PR-версию workflow
или Python-помощника; потребителю добавлены только read-права checks/statuses.

Штатный выпуск сам подмешивает main и меняет строку VERSION; полученный SHA
ожидаемо отличается от принятого source SHA. Обычный push без force отвергает
параллельный сторонний push; `_settled` и атомарный merge с параметром SHA
проверяют именно созданную голову. У созданного version-коммита допустим
`unstable` из-за `[skip ci]`; `blocked`/`behind` запрещены, а все gate-проверки
принятого source SHA остаются обязательными. Version guard загружается из доверенного
main один раз до checkout и переиспользуется, в том числе при retry; PR-версия
Python-guard с повышенным токеном не исполняется.

Сам существующий release pipeline делает checkout ветки для штатного изменения
номера; очередь не добавляет отдельного выполнения PR-кода. Успешное слияние
по-прежнему запускает штатную сборку и проверку сайта. Ни intent, ни dispatch
не являются подтверждением фактического развёртывания.

Проверки: `tests/test_auto_release.py` и
`tests/test_the_release_number_is_issued_at_merge.py`. Установка этой
автоматизации не выдаёт допуск старым PR, включая незавершённые финансовые
задачи. Для каждого нужен актуальный результат и отдельная аттестация контроля.
