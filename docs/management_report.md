# Управленческая сводка (стройка, деньги, продажи, новости)

Идея владельца: еженедельная и ежемесячная сводка по проекту для лиц,
принимающих решения, с рассылкой через бота.

## Решения владельца (20.10.2026)

- Формат: короткое сообщение в Telegram + PDF с подробностями.
  Неделя — понедельник 9:00 МСК, месяц — 1-го числа 9:00 МСК.
- Получатели подписываются по ссылке-приглашению на бота, которую владелец
  создаёт для проекта; владелец видит список и может отписать любого.
- «Физика» стройки — проценты физического выполнения работ, которые ставятся
  в обновлённом ГПР (ГПР-факт), а не объёмы.
- Ручные новости (арбитражи, споры) — лента записей на странице проекта:
  тема, текст, статус, дата, автор.
- Бюджет месяца (20.10.2026): план — из план-факта БДДС; факт — из РСС.
  Стройка — глава 2 РСС без 2.6 против «Стоимости строительства и
  проектирования» без «Содержания службы заказчика». Коммерческие — 3.1, 3.2,
  3.4, 3.7 против «Коммерческих расходов» (3.5 — проценты банка, 3.3 — налоги
  в бюджете вне коммерческих). Статья 2.6 РСС — отдельной строкой без плана:
  в ней и служба заказчика, и офис (АХР бюджета). Сверка сентября 2026:
  стройка 185,3 млн ₽ в бюджете против 182,9 млн ₽ в РСС, коммерческие —
  13,9 против 13,6.

- Бюджет месяца по статьям (контроль, 20.10.2026; карта принята владельцем по
  сверке сентября 2026): каждая статья план-факта БДДС — план месяца, оплачено
  по РСС до даты сводки, остаток, процент; подытог главы — строка главы
  бюджета, итог — стройка и коммерция. Статья бюджета ищется по точному имени
  после строки своей главы (группировка строк не нужна), код РСС — по самому
  длинному совпавшему коду карты `developaid_monthly_budget.ARTICLES`:

  | Статья бюджета | Коды РСС |
  |---|---|
  | Проектные и изыскательские работы, авторский надзор | 2.7 |
  | Основные объекты строительства | 2.2, 2.3, 2.5 |
  | Прочие работы и затраты (содержание стройплощадки) | 2.2.1.10, 2.2.2.8 |
  | Наружные сети и сооружения | 2.4 |
  | Временные здания и сооружения | 2.1 |
  | Реклама и PR (КС) | 3.1 |
  | Расходы на продажу (КС) | 3.2, 3.4 |
  | Персонал и офис отдела продаж (КС, две строки бюджета) | 3.7 |
  | Содержание службы заказчика — вне итога, в 2.6 и офис | 2.6 |

  Код главы 2 или 3.1/3.2/3.4/3.7 вне карты — строка «Без плана: код имя»
  (имя — из листа расчёта стоимости РСС). Месяц тренда раньше первой оплаты
  в реестре — «нет данных», а не 0 ₽; месяц без плана и без данных в начале
  ряда не показывается.

- Оформление (контроль, 20.10.2026): первая страница — восемь плиток по четыре
  в ряд (`tiles`: выполнение стройки, рабочие, продажи к плану ФМ и банка,
  остаток лимита, покрытие кредита эскроу, бюджет стройки и коммерции; цвет —
  по отклонению), затем «Главное» списком с жирным началом. План на графиках —
  пунктир, у последних точек — значения. Стиль документа один
  (`REPORT_STYLE`): страница `/report` берёт его с префиксом `#reportBox`.

- Выполненные за период работы (владелец, 20.10.2026: «А выполняемые за неделю
  работы?»; источник выбран — отчёты бота): строки раздела «По работам»
  ежедневных отчётов за период, по подрядчикам (приписка — правилом Монитора
  `attribute_works`), одинаковая строка за несколько дней — одна строка с
  датами (`crew.works`). Прирост по ГПР-факту и акты КС-2 сюда не входят.

- Фото со стройки (владелец, 20.10.2026: «фото из чата тоже выборочно брать и
  вставлять»; выбор — на странице сводки). Бот сохраняет фото из чата,
  привязанного `/site`: на Render скачивает размер не длиннее 1280 точек и
  отдаёт ядру маршрутом `/internal/monitor/photo` (подпись токеном бота, код
  `monitor-photo`; ядро до Telegram не достаёт). Хранение —
  `developaid_site_photos`: файл + журнал `photos/log.jsonl` под замком.
  В сводку попадает только отмеченное на странице `/report`
  (`/monitor/photos`); не отмечено — блока нет. В PDF фото встраиваются
  в блок «Стройка», в сообщении — их число. Фото, отправленные до выкатки,
  бот не видит: Telegram их задним числом не отдаёт.

- Сроки работ по корпусам (владелец, 20.10.2026: «график как в мониторе, но
  с укрупнёнными статьями по корпусам с планом и прогнозом окончания работ и
  РНВ»). `developaid_report_gantt`: дерево графика из того же среза Монитора,
  что срок и финансирование (`_monitor_view`, один расчёт на сводку); корпус —
  правило Ганта Монитора (`CORPUS_PATTERN` = `corpusLabel`), внутри корпуса —
  статьи РСС, к которым ГПР привязал работы. План — пунктирный контур по
  утверждённому графику, прогноз — сплошная полоса по темпу Монитора, опоздание
  — отдельным цветом; неизвестный прогноз — «нет прогноза», а не плановая дата.
  Опоздание строки — по работам с известным прогнозом против их же плана.
  Веха РНВ — утверждённая и прогнозная (из PM-выгрузки; без неё — пояснение).
  Блок «Стройка» в PDF и на странице, строка на корпус в сообщении, пункт
  «Корпуса» в «Главном». Образец — `docs/samples/report_corpus_gantt_sample.pdf`.

- Выбор проекта (владелец, 21.10.2026: «зачем вручную вбивать два раза
  названия в отчёте? Надо делать выбор из выпадающего окна»). На `/report`
  проект Монитора — выпадающий список того, что лежит в данных Монитора
  (`developaid_monitor.projects`: каталог хотя бы с одним непустым разделом;
  каталог, созданный чтением, проектом не считается). Проект отчёта о
  продажах — тоже список (`sales_store.projects`), и выбирается он один раз:
  связь хранится на сервере в каталоге проекта Монитора (`sales_link.json`,
  `developaid_management_report.link_sales` / `sales_link`; маршруты
  `/monitor/report/projects`, `/monitor/report/link`) и действует для всех,
  для PDF и рассылки. Связи нет — `None` и просьба выбрать; «продаж в сводке
  не нужно» — отдельное решение (пустое имя в записи). Сводка без явного
  `sales_project` берёт связь. Проект по умолчанию — последний открытый в
  этом браузере.

- ГПР сводки = ГПР Монитора (владелец, 21.10.2026: «нельзя ли ГПР взять из
  Монитора? Я вчера 30 сомнительных закрыл там»). Проценты работ — одной
  функцией с Монитором (`manager._baseline_status`): утверждённый ГПР, поверх
  свежайший ГПР-факт не позднее даты сводки, поверх точечные решения Монитора
  (кнопка «закрыть сомнительные» пишет их в `work_fact/`). Без ГПР-факта
  сводка не отказывает, а показывает утверждённый ГПР с решениями и прямо
  говорит об этом; источник с датами — `physical.source.label` («ГПР-факт от …
  и решения в Мониторе по N работам (последнее — …)»), он же подпись пункта
  «Стройка» в «Главном». Карточка «Стройка» на панели Монитора — другой
  показатель (принятые КС к бюджету РСС), с процентом ГПР его не сравнивать.

- Рассылка (волна 3; решения владельца 20.10.2026). `developaid_report_mailing`
  + маршруты в `engine/monitor.py`. Владелец на `/report` (карточка «Рассылка
  руководству») выдаёт ссылку-приглашение `t.me/<бот>?start=rep_<код>`: новая
  ссылка закрывает прежнюю, подписанные остаются; там же список получателей с
  итогом последней сводки и кнопка «Отписать». Получатель жмёт «Старт» —
  бот (Render) передаёт подписку ядру (`/internal/report/subscribe`, подпись
  токеном бота); «/report_stop» — отписка ото всех сводок.
  Ядро до Telegram не достаёт, поэтому: фоновый поток ядра (`_mailing_loop`,
  раз в 2 минуты) после 9:00 МСК понедельника (неделя по воскресенье) и 1-го
  числа (прошлый месяц) собирает сводку и PDF каждого проекта с подписчиками —
  один раз на срок: неблокирующий замок сборки + файл очереди как отметка
  «собрано»; печать занята — повтор до 11:00, потом сообщение с причиной.
  Бот раз в минуту забирает очередь (`/internal/report/outbox`): выдача под
  замком переводит получателей в «передано боту», второй воркер получает
  пустоту; итог по каждому чату бот возвращает (`/internal/report/sent`), и
  владелец видит «отправлено / не отправлено (причина) / отправка не
  подтверждена». Срок досылается 36 часов, старее — уже не новость. Всё — в
  `.mailing/` каталога снимков Монитора на ядре: диск бота стирается выкаткой.
  На ядре нужна переменная `TELEGRAM_BOT_USERNAME` (без неё страница так и
  пишет). Сообщение длиннее предела Telegram уходит частями по строкам.

- Споры и претензии (владелец, 21.10.2026: «Для информации по юр вопросам. Надо
  сводку делать на основе этих документов»; выбран реестр споров с чтением
  документов). `developaid_legal_cases`, карточка «Споры и претензии» на
  `/report`, маршруты `/monitor/legal*`. Юрист загружает документы спора (docx,
  xlsx, PDF, сканы распознаются tesseract на ядре) — новым спором или
  дополнением к существующему; чтение и ответ Платона идут в фоне
  (`legal/jobs/`), страница спрашивает статус. Платон (тот же маршрут модели,
  `_openai_responses_request`, строгая схема `CASE_SCHEMA`; модель —
  `OPENAI_LEGAL_MODEL`, иначе `OPENAI_AGENT_MODEL`) предлагает карточку:
  контрагент, договор, суть, требования с суммами и направлением (наши / к
  нам, «растёт»), хронология писем, следующий шаг и срок, позиция и риск.
  Тексты документов — данные, не инструкции. Документ без текста называется
  с причиной. Человек правит и подтверждает: в сводку идёт только
  подтверждённое (`cases.jsonl`, версии; на конец периода берётся последняя
  версия не позже него). В сводке — только текущий статус (владелец,
  23.10.2026): пункт «Споры» в «Главном», таблица «Споры и претензии» (строка
  на спор: контрагент, предмет, стадия, ближайшая дата, сумма с направлением),
  строка на спор в сообщении. Один спор — одна карточка, склейки нет:
  `docs/legal_cases.md`. Документы хранятся в `legal/docs/` проекта Монитора,
  до 20 МБ каждый.

- Почти нулевой темп (владелец, 21.10.2026, после прогноза РНВ 26.04.2045 «на
  6418 дн. позже» по Кутузов Сити; выбрано «не экстраполировать»). Прогноз
  работы — остаток, делённый на темп актов её статьи за 3 месяца; при темпе
  около нуля он уходил на десятилетия и по сети уводил РНВ. Правило одно для
  Монитора, сценариев и сводки (`developaid_monitor_forecast.pace_finish`):
  если по темпу работа закончилась бы позже `STALL_SPANS` = 3 своих плановых
  длительностей после планового финиша, это «почти стоит» (`stalled_pace`) —
  прогноза числом нет, РНВ она не двигает, плановый срок ей не подставляется.
  Список таких работ — `dashboard.schedule.stalled`; подпись прогноза Монитора
  («без N работ, которые почти стоят») и пункт «Срок» сводки называют их;
  в «сомнительных» Монитора они остаются кандидатами.

- Один проект под двумя именами (владелец, 21.10.2026: «Почему разница между
  Гродненской и Кутузов сити? Это один проект»; главное имя — «Кутузов Сити»).
  Файлы проекта загружали под двумя названиями, и в Мониторе было два каталога.
  На `/report` карточка «Один проект под двумя именами» (видна, когда проектов
  больше одного): «Проверить» показывает план, «Объединить» выполняет
  (`developaid_monitor_merge.merge`, маршрут `/monitor/merge`). В главном ничего
  не перезаписывается: недостающее переезжает, журналы `*.jsonl` дописываются,
  ручные отметки одного дня сливаются (главный сильнее), разное с одним именем
  (например, второй утверждённый ГПР) ложится в `.merged-from-<имя>/` и
  называется. Старое имя — псевдоним в `.aliases.json` каталога снимков, его
  читает `developaid_monitor._project_dir`, единственная дверь к данным
  проекта: чат стройки, бот и ссылки по старому имени попадают в главный.
  Прежний каталог уходит в `.merged/` (откат — руками), запись — в
  `.merged/log.jsonl`. Получатели рассылки и ссылка-приглашение переходят к
  главному.

- Состав PDF и сообщения (владелец, 20.10.2026): Стройка → Продажи →
  Финансирование → Бюджет → Общая информация.

- Сводка — документ для решений (владелец, 20.10.2026: «А где графики?
  Аналитика?»): первая страница «Главное за период» — выводы с числом и
  источником (`findings`), дальше блоки с графиками (`developaid_report_charts`,
  встроенный SVG, одна разметка для страницы и PDF) и динамикой к предыдущему
  периоду. Образец на тестовых данных — `docs/samples/management_report_sample.pdf`.

## Темп продаж: одна мера на экране, три в документе

Владелец (22.10.2026): «может совместить для экономии места? и отдельно
лотами и млн рублей сделать такие же графики? на странице переключением как в
отчёте о продажах, а в пдф подряд три графика». Темп продаж по месяцам — один
предмет в трёх мерах (`PACE_MEASURES`: м², лоты всех типов, млн ₽), на каждом
графике линия цены квартир на своей шкале справа (`charts.bar_chart(...,
line=)`; левая шкала объёма от нуля, шкала цены — от своего минимума).
Разметка одна (`_pace_charts`: `.switch-charts` с кнопками `.switch` и
панелями `.pane`): стиль документа прячет кнопки и показывает все панели
подряд, страница `/report` показывает одну панель и переключает кнопками.
Образец: `docs/samples/report_sales_pace_switch.png`,
`docs/samples/report_sales_pace_sample.pdf`.

## Содержание и страницы документа

Владелец (22.10.2026): «а в начало содержание? в пдф блоки финансирование,
продажи, бюджет и споры и т. д. начинать с новой страницы?». Блоки документа —
один список `BLOCKS` (ключ якоря, заголовок): из него содержание в начале
(`_toc_html`, ссылки на якоря `#block-<ключ>`; номеров страниц нет — Chromium
при печати их не считает, а порядок блоков совпадает с порядком страниц) и
заголовки `_block_heading` с классом `block`. В документе `h2.block` начинает
новую страницу; «Главное за период» (`block first`) остаётся на первой под
плитками. На странице `/report` разрыв гасится, ссылка содержания прокручивает
к блоку. «Споры и претензии» — свой блок перед «Общей информацией».
Образец: `docs/samples/report_contents_page1.png`, `docs/samples/report_contents_sample.pdf`.

## Главы РСС в деньгах стройки

Лимит, оплачено, законтрактовано, утверждённый бюджет и потребность считаются
по главам 1–3, если финансовая книга несёт строку главы 1 («1») рядом с итогом
«Всего инвестиционные расходы глава 2, 3». Нет строки главы 1 — главы 2–3 и у
РСС: оплаченное по главе 1 против бюджета без неё дало бы ложный дефицит.
Набор глав — одно место (`developaid_monitor_dashboard.CHAPTERS`, поле
`chapters` финансового baseline); подписи берут `chapters_label`.

Строкой главы 1 считается «1», а без неё — верхние статьи «1.1», «1.2»… (код в
ячейке может быть числом). Нет ни одной — `chapters_reason` называет это в
подписи плиток («главы 2–3 (без главы 1: … нет строки главы 1)»), а не молча.

Выборка кредита в сводке — платежи РСС из заёмных средств по тем же главам,
что лимит Монитора (признак `payment_in_chapters`); лимит не посчитан — по
всем главам. Остаток лимита — по статьям: лимит статьи минус всё оплаченное
по ней (кредитом и своими деньгами), статья с перерасходом идёт нулём, поэтому
«лимит − выбрано» и «остаток» — не одно вычитание. Монитор раскладывает
разницу (`remaining_check`: перерасход статей, расхождение лимитов статей
финкниги со сметой РСС — с учётом резерва 2.8/2.9, который из статей вынут и
стоит своей строкой; строка равная резерву была бы тем же числом второй раз), плитка «Остаток» называет оплаченное кредитом и
своими деньгами, таблица раздела — все поправки; выборка больше лимита —
плитка «Выбрано» красная с суммой превышения. Образец:
`docs/samples/report_finance_tiles.png`, `docs/samples/report_finance_chapters_sample.pdf`.

## Площадь продаж и месяц отклонений бюджета

Площадь в строках продаж — только у товаров, которые продаются метром
(квартиры, помещения; `contracting.product_measure`). Машиноместа и кладовые
идут штуками рядом, их деньги — в общей сумме. Таблица «Отклонения по статьям
бюджета» — за прошлый месяц относительно даты сводки; нет этого месяца или его
факта в файле БДДС — сводка пишет это, а не берёт последний месяц с фактом.

## Загрузка нескольких файлов БДДС

Файл план-факта БДДС хранится под именем «дата загрузки_первый месяц_последний
месяц». Файлы за разные периоды грузятся в один день; повторная загрузка того
же периода заменяет файл, прежний уходит в `budget/.replaced/`. План месяца
берётся из файла с более поздним периодом (при равном — загруженного позже);
файл, загруженный после даты сводки, в неё не идёт.

## Эскроу против плана банка

План банка по эскроу — строка «Итого остатки на эскроу накопительным итогом
(утверждено по CF)» листа плана банка (`contracting.BANK_ESCROW_LABEL`), в
тысячах рублей, нарастающим по кварталам. Лист ищется по явному списку имён
`contracting.BANK_SHEETS`: «План банка_new», затем прежнее «Модель банка_new».
Сводка сравнивает с ним накопленное на эскроу по графикам договоров на конец
последнего закрытого квартала и показывает план текущего квартала. План листа
«КРЕДИТЫ» финмодели подписан «план финмодели» — под словом «план банка» он не
показывается.

Пустой реестр споров не прячет раздел: сводка пишет «Споры в реестр пока не
внесены…» (вывод «Споры» с пометкой «нет данных»), а если споры есть, но все
закрыты раньше периода, — «Открытых споров нет». Образец:
`docs/samples/report_legal_empty.png`.

## Работы — тому подрядчику, кто назван в строке

Строка работ «Моэк (теплосети) — монтаж ограждения» приписывается названному
подрядчику, только если его имя известно проекту. Список один для Монитора и
сводки (`developaid_monitor_daily.known_parties`): подрядчики, названные
владельцем руками (карточка «Люди на площадке», файл проекта `contractors.json`,
с автором и временем), реестры РСС и ГУ, численность всех ежедневных отчётов до
даты сводки. Неизвестное имя строку не забирает: «Корпус 3 — 3,4,5 эт.»
подрядчиком не становится. Образец: `docs/samples/monitor_declared_contractor.png`.

## Стартовые карточки споров

Реестр споров проекта можно один раз заполнить готовыми карточками из файла на
сервере (`DEVELOPAID_LEGAL_SEED`, по умолчанию `legal_seed.json` в каталоге
снимков Монитора) — только если реестр пуст; метка `legal/.seeded` не даёт
занести их второй раз. Файл в репозиторий не кладётся: репозиторий открытый.
Такие карточки помечены «внесено по документам владельца, юрист ещё не
проверил» в сводке и на странице, пока их не подтвердят правкой.

## Готовые карточки споров файлом

Владелец загружает готовые карточки споров (формат `legal_seed.json`) кнопкой
«Загрузить готовые карточки» в карточке «Споры и претензии» на странице сводки
(`POST /monitor/legal/import`, только владельцу сервиса — `_is_admin_request`).
Карточки проверяются той же схемой, получают пометку «внесено по документам
владельца». Строка файла обновляет карточку только по её номеру (`id` из
выгрузки «Выгрузить карточки файлом») или по ответу владельца на вопрос;
похожая строка без номера не склеивается — подробно в `docs/legal_cases.md`. Файл на сервере (`DEVELOPAID_LEGAL_SEED`) по-прежнему
работает, но положить его при выкатке некому — выкатка идёт образом из main.

Из «cf_1_new» (суммы в тысячах рублей, строки расходов «2.…»): утверждённый

и «Коммерческие расходы» (2.3 → глава 3, «коммерция») по явной карте
`_FM_SECTIONS` (`sections`: всего, оплачено, план и по месяцам); АХР и налоги
(2.4) банк не финансирует, земля (2.1) в вопрос не входит (владелец,

читается в `credit_plan` справочно.

Главы статей — из карты «статьи_БДДС» той же книги (решение владельца:

## Воронка: звонок → встреча → бронь → договор, и менеджеры

Владелец (24.10.2026): «Почему в воронке нет целевых звонков? Звонок — встреча —
бронь»; «и плюс статистика менеджеров». Разобрано на живой выгрузке чата отдела

  только «целевых звонков» — ступень за август и сентябрь терялась. В новых —
  «ЦО за день - 1». Шаблон `_COUNTS["calls"]` берёт все три написания.
- Ежедневный отчёт — сводка отдела, пишет его дежурный (шесть разных авторов,
  ни одного дня с двумя отчётами). Поэтому в дне берётся последний отчёт, а
  автор сообщения — не менеджер сделки.
- Менеджер стоит в скобках у самой брони: «АГЕНТСКАЯ (Помазанова Александра)».
  Порядок слов пишут по-разному («Мария Вольпи» и «Вольпи Мария») — ключ —
  набор слов.
- Площадь брони в отчёте уточняют (кв. 41: «126 кВ.м», назавтра «121.1»), и
  бронь узнаётся по квартире и башне, а не по площади (`_lot_key`). Это же

кабинета: целевые звонки и встречи (сумма по дням), новые брони (квартиры,
впервые попавшие в список за период; брони первого отчёта новыми не считаются),
договоры отдела (подписанные в период), доля каждой ступени от предыдущей.

отчётах не названы»), а не пропускается.

Сводка: строки `_funnel_line` и `_managers_line` в блоке «Продажи». Кабинет:

продаж (`salesRoomBlock`, поле `salesroom.pipeline`). Проверка —
`tests/test_the_funnel_runs_from_call_to_deal.py`.

Воронка рисуется и картинкой (владелец, 24.10.2026: «нарисуй воронку
картинкой»): `charts.funnel_chart` — четыре полосы по центру, длина — число
ступени, между ступенями — доля от предыдущей; ступень, которой нет в отчётах,
— пустая пунктирная рамка «в отчётах нет». Числа — те же, что в строке над
картинкой (`_funnel_figure` читает `pipeline.total`); картинка стоит на
странице и в PDF, в сообщении Telegram остаётся строка.

  финмодель `baseline/finance.xlsx` и её прежние версии, отчёты РСС, файлы
  БДДС, отчёты о продажах, файлы кредита. Дата версии — из имени файла, у
  файла без даты — день загрузки. Где взят план, сводка пишет строкой «График
  взят из: …».
- Загрузка отдельным файлом остаётся заменой на более свежую версию: Монитор,
  блок «Бюджет месяца · раз в месяц», «График финансирования» с датой графика
  (`/monitor/funding-schedule`). Хранятся все версии
  (`funding_schedule/<дата>.xlsx`); та же дата — прежний файл уходит в
  `.replaced/`; загруженный на ту же дату главнее книги, где лист нашёлся
  попутно.
- Графика нет нигде — сводка полной фразой называет, в каких книгах искали
  (и сколько их), какие не загружены и куда можно загрузить файл. Имени листа
  в сводке нет (`docs/plain_language.md`).
- Кабинет продаж хранит только разобранные части книги CF, а не саму книгу:
  если лист лежит только там, его здесь не видно — это названо в тексте
  перечнем книг, где искали.
- Чтение — `developaid_funding_schedule.read_schedule`: колонки и месяцы — по
  словам шапки (строки 2–4, год — объединённой ячейкой над месяцами), не по
  позиции; тройки «Лимит после / Банк / Резерв» — не план. Итог — строка
  «ИТОГО», строки после неё не статьи. Пустая ячейка месяца — «плана нет»,
  текст в числовой ячейке («гар. 5 %») — «нет числа» с примечанием. Единицы —
  из заглавия или шапки («млн», «тыс»); если их нет — по величине итога, и
  это названо в сводке.
- Сверка — одна функция `execution(project, end)`: сводка берёт числа
  только из неё; Монитор пока хранит версии и чисел сверки не показывает —
  если начнёт, читает ту же функцию. Месяц сверяется с версией, выпущенной не позднее его конца (месяцы
  раньше первого графика — с первым). Платёж находит статью графика по дереву
  РСС (код, иначе ближайший предок — порядок строк и глубина, как в
  `developaid_actuals`). Подстроки графика (2.2.1.7.1 и т. п.) — вместе с
  родителем; подстрока, по коду которой реестр платил, — отдельной строкой.
  Один код двумя строками (2.2.2.4.) — одна строка сверки с обеими суммами и
  примечанием. Оплаты по статьям, которых в графике нет, — отдельной суммой в
  примечании месяца. Статья 2.6 — с той же оговоркой об офисе, что в бюджете
  месяца.
- В сводке: таблица месяцев (план из строки «ИТОГО», оплачено, отклонение,
  исполнено; текущий месяц — «месяц не закрыт, оплачено на <дата>»), таблицы
  статей по месяцам и сверка колонки «Выплачено» графика с реестром на дату
  графика (показываются только расхождения и «нет числа»). В сообщении —
  строка об исполнении последних двух месяцев.
- Проверка: `tests/test_the_funding_schedule_is_checked_against_payments.py`
  и `tests/test_the_funding_schedule_is_found_in_the_books.py` на
  синтетическом файле `tests/funding_schedule_fixture.py` (настоящий файл в
  репозиторий не кладётся).

## Эскроу по кварталам: план банка, план финмодели, факт или прогноз

Владелец (26.10.2026) на снимке блока «Финансирование»: «Что за очередь 1?»
и «Сравнивать с планом банка, а не только ФМ, и желательно оба сравнения — с
прогнозом и планом до конца».

- Одна таблица «Эскроу по кварталам» (`_escrow_track`) от первого квартала,
  где есть деньги, до квартала ввода или раскрытия эскроу (что позже):
  «План банка» (строка «…(утверждено по CF)»), «План финмодели» (лист
  «КРЕДИТЫ», нарастающим, сумма очередей), «Факт» (накоплено по графикам
  договоров на конец прошедшего квартала; у текущего — на сейчас), «Прогноз
  при нынешнем темпе» (на конец текущего и будущих кварталов —
  `contracting.keeping_at`, тот же расчёт, что «к вводу» и «к раскрытию») и
  отклонения к обоим планам (факт или прогноз минус план). Плана нет — «нет
  данных», а не ноль.
- Текст сводки (последний закрытый квартал, текущий, квартал ввода или
  раскрытия) и пункт «Главного» читают те же строки.
- Прежние таблицы «Эскроу против плана банка», «Эскроу, очередь» и «Эскроу к
  вводу» сведены в неё и в «Покрытие кредита эскроу» (к раскрытию и к вводу:
  на эскроу при темпе и по плану, кредит, оба покрытия).
- Имя очереди пишется, только если очередей больше одной (`_escrow_of`).
- На телефоне таблица прокручивается в своей рамке. Проверка:
  `tests/test_escrow_by_quarter.py`.

## Ввод к эскроу — утверждённый, прогноз отдельно

Владелец (27.10.2026): «Откуда в сводке взят ввод этот? Ввод в сентябре
2027». Сводка считала эскроу к прогнозу Монитора по темпу работ (15.12.2028),
а утверждённый ввод — сентябрь 2027. Решение: «Ввод — утверждённый, прогноз
отдельно».

- Один источник срока ввода в сводке — `schedule(dashboard)`: блок «Срок»,
  «Покрытие кредита эскроу к вводу» и квартал ввода в «Эскроу по кварталам»
  читают из него утверждённый срок (`_commissioning`). Нет утверждённого
  срока — нет и ответа «к вводу»; прогноз его не заменяет.
- Прогноз Монитора, если он позже утверждённого, — отдельной строкой рядом
  (`_forecast_shift`, `_shift_lines`): «По темпу работ ввод может сдвинуться
  на … (прогноз Монитора) — срок тянет работа «…» (объект; статья сметы …):
  принято N % объёма, по нынешнему темпу закончится … вместо … по плану».
  Таблицу по кварталам прогноз не удлиняет.
- Второе число — покрытие к дате прогноза: накоплено + темп × месяцев до неё
  против кредита перед погашением (остаток по плану финмодели на месяц
  раскрытия). План кредита на саму дату прогноза не берётся: он уже гасит
  кредит из эскроу с утверждённого ввода. Проценты за лишние месяцы в этом
  числе не учтены. В таблице «Покрытие кредита эскроу» — строка «если ввод
  сдвинется на …».
- Работу, которая тянет срок, называет Монитор (`dashboard.schedule.driver`,
  `developaid_monitor_pace._driver`): след от вехи ввода назад по той же сети,
  что дала прогноз (`developaid_monitor_schedule_graph.driver`) — к
  предшественнику, чья связь задала прогнозный старт, пока не найдётся работа,
  сдвинутая собственным прогнозом, а не сетью. Один проход по посчитанной сети
  (доли миллисекунды); ранжирование сценариев (`_forecast_drivers`) — 20+
  прогонов сети, на каждую сборку Монитора его не зовут. Без PM-сети — строка с
  самым поздним прогнозным финишем. Ввод в срок — работа не называется. Её же называет пункт «Срок» в «Главном» и пояснение под
  графиком в блоке стройки.
- Статья сметы рядом с работой — потому что «принято N %» считается по ней:
  неверная привязка работы к статье (несколько работ на одну крупную статью)
  дала бы малый процент и далёкий прогноз, и её видно сразу.
- «Почти стоит» — по-прежнему прогноз дальше трёх своих плановых
  длительностей после плана (`forecast.STALL_SPANS`, решение 21.10.2026).
  Работа, опаздывающая меньше, — настоящий прогноз и РНВ двигает; порог —
  решение владельца, сводка его не меняет.
- Раскрытие раньше ввода объяснено словами: раскрытие по плану кредита — месяц
  перед первым погашением, на нём на эскроу ещё лежит всё накопленное
  (`_disclosure_order_words`). При вводе в сентябре и погашении с сентября это
  август.
- Проверка: `tests/test_the_commissioning_is_approved_and_the_forecast_apart.py`,
  `tests/test_the_escrow_is_told_at_commissioning.py`.

## Прогноз эскроу: рассрочка к вводу; раскрытие в таблице по кварталам

Владелец (27.10.2026): «В прогнозе эскроу никак не учитывается, что 1,5 млрд
на эскроу сейчас при продажах 2,5. Причина в рассрочке, которая должна быть
погашена при вводе». На вопрос, как раскладывать остаток, — «Равномерно до
ввода». И на провале «Плана финмодели» 7,31 → 1,96 млрд в квартале раскрытия:
«И получается бред. По прогнозу ФМ нет уточнения, что она тут гасит долг».

- Прогноз эскроу при известном сроке ввода (`contracting.keeping_at` с
  `settle`, один расчёт для кварталов, «к раскрытию», «к вводу» и строки
  «если ввод сдвинется»): накоплено на месяц данных плюс остаток к оплате по
  подписанным договорам (`owed_by_contracts`: сумма договора минус большее из
  «оплачено эскроу всего» и графика поступлений; расторгнутых в контрактации
  нет) плюс новые продажи по нынешнему темпу подписания (сумма договоров за
  те же полные месяцы, что темп) до ввода. Деньги приходят равномерно по
  месяцам до ввода, к вводу всё на эскроу, после ввода прироста нет.
- Срок ввода — утверждённый (см. раздел выше); у строки «если ввод
  сдвинется» рассрочку гасят к дате прогноза.
- Без срока ввода — прежнее продолжение темпа поступлений, и это сказано
  словами. Кабинет продаж срока ввода не знает и считает по-прежнему.
- Подписи «при нынешнем темпе» у эскроу заменены на «по прогнозу»; как
  построен прогноз — одна фраза `_forecast_method_words` под таблицей и в
  тексте сообщения.
- Раскрытие. Какую величину даёт каждая колонка, видно по рядам: план банка —
  строка «Итого остатки на эскроу накопительным итогом (утверждено по CF)»,
  факт и прогноз — накопленное по договорам, план финмодели — «Счета эскроу
  (нараст)» листа «КРЕДИТЫ», и на месяце раскрытия этот ряд падает (эскроу
  уходит в погашение). Провал ищется по самим числам (`_disclosure_step`:
  остаток на эскроу и кредита на месяц раскрытия и следующий). Есть провал —
  в квартале раскрытия план финмодели взят на месяц раскрытия с пометкой «до
  раскрытия», отклонение к нему — «нет данных», в кварталах после —
  «нет данных» с причиной; под таблицей и в тексте: «Раскрытие эскроу, <месяц>:
  по плану финмодели на эскроу X, в <следующем> — Y: раскрыто X − Y, из них на
  погашение кредита Z (остаток кредита с … до …)». Провала нет — ряд
  накопленный и сравнивается до конца.
- Ввод позже такого раскрытия (утверждённый ввод — сентябрь 2027, раскрытие —
  август 2027): «к вводу» сравнивается с планом финмодели и кредитом на месяц
  раскрытия, до погашения (`_repaid_after`), и это подписано «план — на …, до
  раскрытия». Строка «если ввод сдвинется» берёт кредит так же.
- Проверка: `tests/test_the_escrow_forecast_counts_the_installments.py`
  (провал ряда без пояснения роняет проверку).
