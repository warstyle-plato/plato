# Управленческая сводка (стройка, деньги, продажи, новости)

Идея владельца: еженедельная и ежемесячная сводка по проекту для лиц,
принимающих решения, с рассылкой через бота.

## Решения владельца (20.10.2026)

- Формат: короткое сообщение в Telegram + PDF с подробностями.
  Неделя — понедельник 9:00 МСК, месяц — 1-го числа 9:00 МСК.
- Получатели подписываются по ссылке-приглашению на бота, которую владелец
  создаёт для проекта; владелец видит список и может отписать любого.
- «Физика» стройки — проценты физического выполнения работ, которые ставятся
  в обновлённом ГПР (ГПР-факт), а не объёмы.
- Ручные новости (арбитражи, споры) — лента записей на странице проекта:
  тема, текст, статус, дата, автор.
- Бюджет месяца (20.10.2026): план — из план-факта БДДС; факт — из РСС.
  Стройка — глава 2 РСС без 2.6 против «Стоимости строительства и
  проектирования» без «Содержания службы заказчика». Коммерческие — 3.1, 3.2,
  3.4, 3.7 против «Коммерческих расходов» (3.5 — проценты банка, 3.3 — налоги
  в бюджете вне коммерческих). Статья 2.6 РСС — отдельной строкой без плана:
  в ней и служба заказчика, и офис (АХР бюджета). Сверка сентября 2026:
  стройка 185,3 млн ₽ в бюджете против 182,9 млн ₽ в РСС, коммерческие —
  13,9 против 13,6.

- Бюджет месяца по статьям (контроль, 20.10.2026; карта принята владельцем по
  сверке сентября 2026): каждая статья план-факта БДДС — план месяца, оплачено
  по РСС до даты сводки, остаток, процент; подытог главы — строка главы
  бюджета, итог — стройка и коммерция. Статья бюджета ищется по точному имени
  после строки своей главы (группировка строк не нужна), код РСС — по самому
  длинному совпавшему коду карты `developaid_monthly_budget.ARTICLES`:

  | Статья бюджета | Коды РСС |
  |---|---|
  | Проектные и изыскательские работы, авторский надзор | 2.7 |
  | Основные объекты строительства | 2.2, 2.3, 2.5 |
  | Прочие работы и затраты (содержание стройплощадки) | 2.2.1.10, 2.2.2.8 |
  | Наружные сети и сооружения | 2.4 |
  | Временные здания и сооружения | 2.1 |
  | Реклама и PR (КС) | 3.1 |
  | Расходы на продажу (КС) | 3.2, 3.4 |
  | Персонал и офис отдела продаж (КС, две строки бюджета) | 3.7 |
  | Содержание службы заказчика — вне итога, в 2.6 и офис | 2.6 |

  Код главы 2 или 3.1/3.2/3.4/3.7 вне карты — строка «Без плана: код имя»
  (имя — из листа расчёта стоимости РСС). Месяц тренда раньше первой оплаты
  в реестре — «нет данных», а не 0 ₽; месяц без плана и без данных в начале
  ряда не показывается.

- Оформление (контроль, 20.10.2026): первая страница — восемь плиток по четыре
  в ряд (`tiles`: выполнение стройки, рабочие, продажи к плану ФМ и банка,
  остаток лимита, покрытие кредита эскроу, бюджет стройки и коммерции; цвет —
  по отклонению), затем «Главное» списком с жирным началом. План на графиках —
  пунктир, у последних точек — значения. Стиль документа один
  (`REPORT_STYLE`): страница `/report` берёт его с префиксом `#reportBox`.

- Выполненные за период работы (владелец, 20.10.2026: «А выполняемые за неделю
  работы?»; источник выбран — отчёты бота): строки раздела «По работам»
  ежедневных отчётов за период, по подрядчикам (приписка — правилом Монитора
  `attribute_works`), одинаковая строка за несколько дней — одна строка с
  датами (`crew.works`). Прирост по ГПР-факту и акты КС-2 сюда не входят.

- Фото со стройки (владелец, 20.10.2026: «фото из чата тоже выборочно брать и
  вставлять»; выбор — на странице сводки). Бот сохраняет фото из чата,
  привязанного `/site`: на Render скачивает размер не длиннее 1280 точек и
  отдаёт ядру маршрутом `/internal/monitor/photo` (подпись токеном бота, код
  `monitor-photo`; ядро до Telegram не достаёт). Хранение —
  `developaid_site_photos`: файл + журнал `photos/log.jsonl` под замком.
  В сводку попадает только отмеченное на странице `/report`
  (`/monitor/photos`); не отмечено — блока нет. В PDF фото встраиваются
  в блок «Стройка», в сообщении — их число. Фото, отправленные до выкатки,
  бот не видит: Telegram их задним числом не отдаёт.

- Сроки работ по корпусам (владелец, 20.10.2026: «график как в мониторе, но
  с укрупнёнными статьями по корпусам с планом и прогнозом окончания работ и
  РНВ»). `developaid_report_gantt`: дерево графика из того же среза Монитора,
  что срок и финансирование (`_monitor_view`, один расчёт на сводку); корпус —
  правило Ганта Монитора (`CORPUS_PATTERN` = `corpusLabel`), внутри корпуса —
  статьи РСС, к которым ГПР привязал работы. План — пунктирный контур по
  утверждённому графику, прогноз — сплошная полоса по темпу Монитора, опоздание
  — отдельным цветом; неизвестный прогноз — «нет прогноза», а не плановая дата.
  Опоздание строки — по работам с известным прогнозом против их же плана.
  Веха РНВ — утверждённая и прогнозная (из PM-выгрузки; без неё — пояснение).
  Блок «Стройка» в PDF и на странице, строка на корпус в сообщении, пункт
  «Корпуса» в «Главном». Образец — `docs/samples/report_corpus_gantt_sample.pdf`.

- Выбор проекта (владелец, 21.10.2026: «зачем вручную вбивать два раза
  названия в отчёте? Надо делать выбор из выпадающего окна»). На `/report`
  проект Монитора — выпадающий список того, что лежит в данных Монитора
  (`developaid_monitor.projects`: каталог хотя бы с одним непустым разделом;
  каталог, созданный чтением, проектом не считается). Проект отчёта о
  продажах — тоже список (`sales_store.projects`), и выбирается он один раз:
  связь хранится на сервере в каталоге проекта Монитора (`sales_link.json`,
  `developaid_management_report.link_sales` / `sales_link`; маршруты
  `/monitor/report/projects`, `/monitor/report/link`) и действует для всех,
  для PDF и рассылки. Связи нет — `None` и просьба выбрать; «продаж в сводке
  не нужно» — отдельное решение (пустое имя в записи). Сводка без явного
  `sales_project` берёт связь. Проект по умолчанию — последний открытый в
  этом браузере.

- ГПР сводки = ГПР Монитора (владелец, 21.10.2026: «нельзя ли ГПР взять из
  Монитора? Я вчера 30 сомнительных закрыл там»). Проценты работ — одной
  функцией с Монитором (`manager._baseline_status`): утверждённый ГПР, поверх
  свежайший ГПР-факт не позднее даты сводки, поверх точечные решения Монитора
  (кнопка «закрыть сомнительные» пишет их в `work_fact/`). Без ГПР-факта
  сводка не отказывает, а показывает утверждённый ГПР с решениями и прямо
  говорит об этом; источник с датами — `physical.source.label` («ГПР-факт от …
  и решения в Мониторе по N работам (последнее — …)»), он же подпись пункта
  «Стройка» в «Главном». Карточка «Стройка» на панели Монитора — другой
  показатель (принятые КС к бюджету РСС), с процентом ГПР его не сравнивать.

- Рассылка (волна 3; решения владельца 20.10.2026). `developaid_report_mailing`
  + маршруты в `engine/monitor.py`. Владелец на `/report` (карточка «Рассылка
  руководству») выдаёт ссылку-приглашение `t.me/<бот>?start=rep_<код>`: новая
  ссылка закрывает прежнюю, подписанные остаются; там же список получателей с
  итогом последней сводки и кнопка «Отписать». Получатель жмёт «Старт» —
  бот (Render) передаёт подписку ядру (`/internal/report/subscribe`, подпись
  токеном бота); «/report_stop» — отписка ото всех сводок.
  Ядро до Telegram не достаёт, поэтому: фоновый поток ядра (`_mailing_loop`,
  раз в 2 минуты) после 9:00 МСК понедельника (неделя по воскресенье) и 1-го
  числа (прошлый месяц) собирает сводку и PDF каждого проекта с подписчиками —
  один раз на срок: неблокирующий замок сборки + файл очереди как отметка
  «собрано»; печать занята — повтор до 11:00, потом сообщение с причиной.
  Бот раз в минуту забирает очередь (`/internal/report/outbox`): выдача под
  замком переводит получателей в «передано боту», второй воркер получает
  пустоту; итог по каждому чату бот возвращает (`/internal/report/sent`), и
  владелец видит «отправлено / не отправлено (причина) / отправка не
  подтверждена». Срок досылается 36 часов, старее — уже не новость. Всё — в
  `.mailing/` каталога снимков Монитора на ядре: диск бота стирается выкаткой.
  На ядре нужна переменная `TELEGRAM_BOT_USERNAME` (без неё страница так и
  пишет). Сообщение длиннее предела Telegram уходит частями по строкам.

- Почти нулевой темп (владелец, 21.10.2026, после прогноза РНВ 26.04.2045 «на
  6418 дн. позже» по Кутузов Сити; выбрано «не экстраполировать»). Прогноз
  работы — остаток, делённый на темп актов её статьи за 3 месяца; при темпе
  около нуля он уходил на десятилетия и по сети уводил РНВ. Правило одно для
  Монитора, сценариев и сводки (`developaid_monitor_forecast.pace_finish`):
  если по темпу работа закончилась бы позже `STALL_SPANS` = 3 своих плановых
  длительностей после планового финиша, это «почти стоит» (`stalled_pace`) —
  прогноза числом нет, РНВ она не двигает, плановый срок ей не подставляется.
  Список таких работ — `dashboard.schedule.stalled`; подпись прогноза Монитора
  («без N работ, которые почти стоят») и пункт «Срок» сводки называют их;
  в «сомнительных» Монитора они остаются кандидатами.

- Один проект под двумя именами (владелец, 21.10.2026: «Почему разница между
  Гродненской и Кутузов сити? Это один проект»; главное имя — «Кутузов Сити»).
  Файлы проекта загружали под двумя названиями, и в Мониторе было два каталога.
  На `/report` карточка «Один проект под двумя именами» (видна, когда проектов
  больше одного): «Проверить» показывает план, «Объединить» выполняет
  (`developaid_monitor_merge.merge`, маршрут `/monitor/merge`). В главном ничего
  не перезаписывается: недостающее переезжает, журналы `*.jsonl` дописываются,
  ручные отметки одного дня сливаются (главный сильнее), разное с одним именем
  (например, второй утверждённый ГПР) ложится в `.merged-from-<имя>/` и
  называется. Старое имя — псевдоним в `.aliases.json` каталога снимков, его
  читает `developaid_monitor._project_dir`, единственная дверь к данным
  проекта: чат стройки, бот и ссылки по старому имени попадают в главный.
  Прежний каталог уходит в `.merged/` (откат — руками), запись — в
  `.merged/log.jsonl`. Получатели рассылки и ссылка-приглашение переходят к
  главному.

- Состав PDF и сообщения (владелец, 20.10.2026): Стройка → Продажи →
  Финансирование → Бюджет → Общая информация.

- Сводка — документ для решений (владелец, 20.10.2026: «А где графики?
  Аналитика?»): первая страница «Главное за период» — выводы с числом и
  источником (`findings`), дальше блоки с графиками (`developaid_report_charts`,
  встроенный SVG, одна разметка для страницы и PDF) и динамикой к предыдущему
  периоду. Образец на тестовых данных — `docs/samples/management_report_sample.pdf`.

## Откуда числа (один владелец у каждого)

| Блок | Источник | Функция |
|---|---|---|
| Сроки работ по корпусам | дерево графика среза Монитора (`schedule.management` после слоя темпа) | `developaid_report_gantt.model` |
| Физическое выполнение | ГПР-факт `schedule_fact/*.xlsx` + точечные факты `work_fact/` | `manager._baseline_status(project, upto)` |
| План выполнения | даты утверждённого ГПР | `monitor._plan_progress` |
| Бюджет месяца: план | план-факт БДДС (файл раз в месяц, `POST /monitor/budget`) | `developaid_monthly_budget.read_budget` |
| Бюджет месяца: факт | реестр платежей РСС по явной карте кодов | `developaid_monthly_budget.line_of` |
| Бюджет месяца по статьям | статьи БДДС по имени + карта кодов РСС | `developaid_monthly_budget.month_articles`, `article_of` |
| Выполненные работы за период | раздел «По работам» ежедневных отчётов бота | `developaid_management_report._works_done` |
| Фото со стройки | фото из чата стройки, отмеченные на странице сводки | `developaid_site_photos.for_report` |
| Общая информация | журнал записей `notes/log.jsonl` проекта мониторинга (`POST /monitor/notes`) | `developaid_project_notes.for_period` |
| Финансирование: выборка кредита | платежи РСС из заёмных средств (за период / месяц / с начала) | `developaid_management_report.funding` |
| Финансирование: услуги банка | платежи РСС статьи 3.5 (в ней проценты) | там же |
| Финансирование: лимит, остаток, дефицит | карточка финансирования Монитора (`dashboard._funding_risk`) | `_monitor_funding` |
| Финансирование: эскроу и покрытие кредита | лист «КРЕДИТЫ» финмодели против эскроу по договорам | `contracting.escrow_sufficiency` |
| Продажи факт | контрактация из склада отчёта о продажах | `contracting._totals` |
| План ФМ | помесячный план финмодели | `contracting.fm_plan_by_month` |
| План банка | квартальный, валовые продажи | `bank_plan.gross_by_quarter`; первый квартал банка — остаток, не квартал |

Сводку собирает `developaid_management_report.build`, текст сообщения —
`render_text`, документ — `render_html`: его показывает отдельная страница
«Сводка руководству» `/report` (вход в контуре в разделе «Строителю», там же
записи «Общая информация»; владелец 20.10.2026 — не смешивать со стройкой),
данные — `POST /monitor/report` и печатает PDF
(`POST /monitor/report.pdf`, сервер, Chromium, очередь печати общая с отчётом
о продажах). Общий процент выполнения — среднее по работам с весом
длительности работы (стоимости у работы в ГПР нет).

## Волны

1. Модель сводки и текст (этот модуль).
2. Лента ручных новостей проекта с автором и датой.
3. Подписка по ссылке-приглашению и рассылка по расписанию без двойной
   отправки (два воркера: замок и отметка «отправлено» на диске), PDF в фоне —
   сделано, см. «Рассылка» выше.
4. Страница просмотра сводки и связь проекта мониторинга с проектом отчёта
   о продажах (явная, имена складов разные).
