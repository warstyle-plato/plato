# DevelopAid 2.0 — интерфейс живого движка

## Назначение

`/v2` — новый мобильный и desktop-интерфейс DevelopAid. Он не считает
экономику: вводные уходят в действующий расчётный движок, и на экран приходит
единственный сериализуемый результат — **ProjectResult**. Формулы движка,
Excel-книга, PDF и Telegram-сценарии этой веткой не изменялись.

```
ProjectInputs (inputs / tep / rates / phasing)
    ↓
main_legacy._run_authoritative_model   ← действующий движок, один вызов
    ↓
ProjectResult
    ├── PWA /v2
    ├── PDF
    ├── Telegram
    └── Платон
```

## Точка входа движка

Адаптер зовёт `main_legacy._run_authoritative_model(inputs, tep, rates,
phasing)` — ту же функцию, которой пользуются Telegram-карточка, PDF-отчёт и
сверка Excel-книги (`_telegram_send_attachments`). Она сама решает, считать
проект одной очередью (`calculate`) или несколькими (`calculate_phased`), и
возвращает `{mode, consolidated, phases, comparison, phasing}`.

Tornado считает `main_legacy.run_sensitivity` — отдельным анализом, по флагу
запроса: он гоняет движок по одному параметру за расчёт и нужен не при каждом
пересчёте.

## Где формируется ProjectResult

`developaid_v2_result.build_project_result` — единственное место сборки.
Модуль **не считает**: он раскладывает результат движка по стабильной схеме,
не пересчитывая и не переводя единицы. Деньги отдаются в рублях так, как их
посчитал движок, доли (маржа, ставки, LLCR) остаются долями; единицы
объявлены полем `units`. Правило охраняется тестом
`test_the_adapter_contains_no_arithmetic`: в модуле не должно быть ни одной
арифметической операции. Форматирование — дело интерфейса.

`calculation_id` берётся у движка — `_calculation_fingerprint(inputs, tep,
phasing)`, тот же идентификатор печатают PDF и книга. Вопрос «один ли это
расчёт» решается сравнением строки, а не сверкой цифр. `input_hash` —
отдельная величина: полный sha256 всех вводных вместе с кривой ставок.

Состав ProjectResult:

| Блок | Что внутри |
| --- | --- |
| происхождение | `schema_version`, `calculation_id`, `engine_version`, `engine_entry_point`, `calculated_at`, `input_hash`, `source`, `prototype`, `units` |
| проект | `project` — название, регион, кадастровые номера, источник ТЭП, сценарий |
| вводные | `request` — `inputs` / `tep` / `rates` / `phasing` (очереди — уже достроенные движком) |
| ТЭП | `tep` (строки, итоги, ГНС наземной и подземной части) |
| ВРИ и социалка | `vri` (график, итоги, источники финансирования), `social` (программа, режим, расшифровка) |
| выручка | `revenue` — итог, по продуктам, продуктовый отчёт, продукты по очередям |
| CAPEX | `capex` — итог, постатейно, структура расходов, стройка, коммерческие |
| KPI | `summary` целиком и `kpi` — выручка, CAPEX, EBITDA, проценты и комиссии, налог, чистая прибыль, маржинальность, NPV, LLCR, IRR, стоимость проекта |
| финансирование | `financing` — расчётный и фактический БРИДЖ, капитализированный БРИДЖ, пик и лимит ПФ, непокрытый эскроу пик, остаток долга, ставки |
| помесячные ряды | `monthly` — месяцы, cash flow проекта и капитала, налог, остатки БРИДЖа и ПФ, эскроу, покрытие, ставки, постатейная детализация |
| очереди | `queues` — по каждой очереди её собственный результат движка: KPI, ТЭП, ВРИ, продукты, финансирование, календарь, помесячные ряды, строка сравнения |
| анализ | `sensitivity` — Tornado движка (или `sensitivity_error`) |
| выводы | `warnings` и `verdict` — инвестиционный вывод функцией движка `_purchase_feasibility` |

## Маршруты

| Маршрут | Назначение |
| --- | --- |
| `POST /api/v2/calculate` | production: вводные мини-приложения → ProjectResult |
| `GET /api/v2/projects` | каталог демонстрационных **вводных** (без показателей) |
| `GET /api/v2/projects/{slug}` | те же вводные, посчитанные движком → ProjectResult |
| `POST /api/v2/tep-search` | «Поиск ТЭП» — точка кнопки бота «Посчитать ВРИ и ТЭП» |
| `GET /api/v2/prototype/projects/{slug}` | контрольные fixtures прототипа, dev-only |
| `GET /v2`, `/v2/assets/*` | статика интерфейса |

`POST /api/v2/calculate` принимает ровно тот payload, который действующее
мини-приложение шлёт в `/calculate-phased`: `inputs`, `tep`, `rates`,
`phasing`. Дополнительные поля (`project_name`, `region`,
`cadastral_numbers`, `source_label`, `scenario`) в расчёте не участвуют — они
едут с результатом, чтобы отчёт знал, о чём он. `sensitivity: false`
отключает Tornado.

Все ответы отдаются с `Cache-Control: no-store`: устаревший ProjectResult на
экране — это ровно тот второй источник цифр, ради устранения которого `/v2`
переведён на движок.

## Контрольные fixtures

Показатели приёмочных PDF от 02.08.2026 переехали в
`developaid_v2_prototype_fixtures.py` и помечены `prototype`. Production их не
отдаёт: маршрут `/api/v2/prototype/...` включается только переменной
`DEVELOPAID_V2_PROTOTYPE_FIXTURES=1`, а тест
`test_production_endpoints_do_not_serve_fixtures` проверяет, что они не могут
прийти как расчёт.

## Демонстрационные проекты

`developaid_v2_demo.py` держит **вводные** двух контрольных проектов, а не их
результаты:

- ТЭП и плата за ВРИ — из серверных предустановок `presets/*.xlsx` разбором
  движка (`parse_glavapu_xlsx`) и его же картой `mappings`. Так же
  предустановку применяет Telegram-поток;
- конфигурация проекта (округ, офисы, очереди 40/32/28, рабочая социалка) —
  та же, что применяет мини-приложение в `applyServerPresetProjectConfig`;
- всё остальное — `DEFAULT_INPUTS` и `TEP_DEFAULT` движка.

Поэтому показатели демонстрационных проектов совпадают с расчётом движка на
этих вводных, а **не** с контрольными PDF: часть вводных приёмочных расчётов
(цена входа, цены продаж, себестоимость наземного строительства) жила в
состоянии страницы, и в репозитории её нет. Подгонять числа под отчёт нельзя:
это вернуло бы второй источник экономики.

## Чего интерфейс не делает

`frontend_v2/app.js` отправляет вводные и рисует поля ProjectResult.
Единственная арифметика в файле — форматирование (рубли в миллиарды) и
геометрия графиков (доли круга, координаты точек). Вердикт, предупреждения,
доли расходов и сравнение очередей приходят из результата, а не собираются на
странице. Версия движка, идентификатор расчёта, время и отпечаток вводных
видны в шапке.

## Что осталось за рамками

1. Форма вводных в `/v2`: `window.DevelopAidV2.calculateProject(payload)` —
   готовая точка входа, интерфейс редактирования делается отдельно.
2. Полное воспроизведение приёмочных расчётов Мишина и Мытищи требует
   вводных, которых нет в репозитории.
3. Excel в задачу не входит: `/v2` не читает результаты книги и не ждёт
   устранения расхождений XLSX.
