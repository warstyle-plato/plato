# Градостроительный скрининг участка — архитектура (владелец, 16.08.2026)

Цель: не заменить архитектора и не доказать, что ТЭП садится, а автоматически
собрать максимум объективных ограничений по кадастру/координате и показать
инвестору ранние red flags до глубокой градпроработки.

Источники делятся на два класса:
1. Runtime-источники — опрашиваются автоматически при каждом расчёте.
2. Нормативная локальная база — поддерживается нами из официальных документов.

Целевая архитектура источников (решение владельца, 17.08.2026):
- **Москва** → ГИСОГД Москвы (gisogd.mos.ru) + НСПД;
- **Московская область** → РГИС МО (rgis.mosreg.ru) + НСПД;
- **РНГП МО** → наша локальная versioned rule-base (раздел 7).
НСПД нужна прежде всего для ЕГРН и реестровых ограничений; градостроительные
данные (ПЗЗ, генплан, ППТ, красные линии) — с региональных геопорталов.
Для обоих регионов порядок один: сначала исследуем публичную карту
(фактические browser-запросы), собственную базу из PDF строим только там,
где проба показала, что машиночитаемого источника нет.

Конвейер: кадастр/координата → ЕГРН/НСПД → ЗОУИТ → ПЗЗ/территориальная зона →
красные линии/ППТ (если доступны) → окружающая застройка → рельеф →
нормативы РНГП → отдельные checks → итоговый screening.

## Решение о порядке работы (17.08.2026)
Вопрос «нужны ли геопорталы» решён: **основной скрининг делаем на НСПД,
геопорталы — запасной путь только под числовые параметры застройки.**
Красные флаги (ЗОУИТ, ООПТ, вода, красные линии, тип территориальной зоны)
целиком берутся из НСПД, к которому доступ с ядра уже есть, — без SSO
Москвы и документной модели РГИС. Порядок:
1. Скрининг строим на слоях НСПД (см. раздел 1). Ничего не блокирует.
2. Первый тест реализации — `GetFeatureInfo` по слою «Территориальные зоны»
   с ядра: несёт ли он числовой регламент (высота/%/плотность/ВРИ) или
   только индекс зоны + ссылку на документ.
3. Геопорталы (разделы 2–3) подключаем ТОЛЬКО если параметров в НСПД нет
   И нужна автопроверка «ТЭП влезает в регламент» (в MVP она отложена).
Контракт РГИС/ГИСОГД задокументирован (разделы 2–3) и ждёт готовым на
случай пункта 3 — переоткрывать разбор не требуется.

**Инструмент для шага 2 готов (17.08.2026): `GET /land/screen-probe`.**
Диагностический маршрут (как `/land/map-probe`): по точке `lat/lng` шлёт
`GetFeatureInfo` слоям-кандидатам НСПД и возвращает по каждому http/число
объектов/ключи и образец `properties` первого объекта. С Render и телефона
НСПД закрыт WAF — запрос форвардится на ядро. Список слоёв — `?layers=имя=номер,…`,
дефолт — `_NSPD_SCREEN_LAYER_CANDIDATES` (пока 36048 подтверждён + кандидаты
37577–37581). Реестр номеров — кандидаты, подтверждает только живой ответ.
Запуск: `curl -sS "http://localhost:8080/land/screen-probe?cad=<номер>"`.

**Схема полей ЗОУИТ подтверждена (проба 17.08.2026, участок
50:20:0070312:8320 → приаэродромная территория Внуково, слой 37581).**
GetFeatureInfo (v3) отдаёт `properties.options` с полями:
- `type_zone` — тип зоны («Приаэродромная территория», «Охранная зона …»);
- `name_by_doc` — наименование по документу (подзона и т.п.);
- `reg_numb_border` / `descr` — реестровый номер границы (50:00-6.3453);
- `content_restrict_encumbrances` — текст ограничения;
- `legal_act_document_name/number/date/issuer` — документ-основание;
- `categoryName`, `type_boundary_value` — «Зоны с особыми условиями …».

Движковая функция `_land_zouit_findings(lat, lng)` собирает эти поля по всем
подслоям ЗОУИТ (`_NSPD_ZOUIT_LAYERS`), дедуплицирует по реестровому номеру,
пропускает слои с ошибкой (один подслой отвечал 400). Это первый рабочий чек
скрининга: «участок пересекает ЗОУИТ типа X, № Y, основание Z». Дальше —
классификация (killer/экономический) и % накрытия геометрией, затем UI-блок.

**Какие номера слоёв нужны, а какие нет (решение 17.08.2026, уточнено).**
Гоняться за каждым номером НЕ нужно, но покрытие должно быть полным — красные
линии и природоохранные в scope, не откладываются (замечание владельца).
Расклад:
- **природоохранные-ЗОУИТ уже ловятся**: подслой «ЗОУИТ природных территорий»
  и водоохранные входят в семью ЗОУИТ (37577–81), тип приходит в `type_zone`,
  их берёт `_land_zouit_findings` уже сейчас;
- **ООПТ** (особо охраняемые природные территории) — отдельный верхний слой
  НСПД, свой номер, добавить;
- **красные линии** — отдельный слой под «Планировкой территории», свой номер,
  добавить (флаг RED_LINE_DETECTED; полнота внесения в ЕГРН фрагментарна —
  говорить об этом честно, но чек делать);
- **терр. зоны** (875838) — тип Ж/О/П;
- **красные линии** — **879243**, **ООПТ** — **875845**, охотничьи угодья —
  875847 (не флаг, записан справочно): снято с карты 17.08.2026 (включить
  слой, прочитать номер в его wms-запросе). Остаются лесничества и береговые
  линии — тем же способом. Номера тематических слоёв лежат кучно около
  875–880 тысяч, но не подряд.

**Автоматический путь к реестру закрыт окончательно (17.08.2026).** Обход
кусков сборки на уровень глубже дал ноль: в entry-файлах нет ссылок на другие
чанки (`grep` по `assets/*.js` — пустой список). Проверен и главный чанк-инициатор
`assets/map/assets/shared-deps-*.js` (537 КБ) — ни номеров, ни названий слоёв.
Значит, список слоёв приходит с сервера при старте карты, и единственный
рабочий способ — ручной: включить слой и прочитать номер в его wms-запросе.

**Единого identify у портала НЕТ — проверено (17.08.2026).** Гипотеза «клик
возвращает 5 объектов одним вызовом, надо поймать этот XHR» опровергнута:
поиск в Network по `identify`/`feature`/`search` даёт только JS-чанки сборки,
а при клике с 17 включёнными слоями летят одни `wms`-запросы — по одному на
слой. То есть портал делает ровно то же, что и мы: `GetFeatureInfo` на каждый
слой отдельно, а «Найдено объектов: 5» — это склейка ответов в интерфейсе.
Вывод: наш поштучный опрос слоёв — не обходной путь, а тот же механизм;
искать в браузере больше нечего, нужны только номера слоёв.

**Причина отказов — наш Referer, а не блокировка НСПД (17.08.2026, проверено
прямым запросом).** Весь день WMS `GetFeatureInfo` отвечал отказом на все
тематические слои, и это читалось как «портал придушил ядро за частые
запросы». Неверно. Два curl с ядра, отличающиеся только заголовком:
- `Referer: …/map?thematic=PKK` (наш прежний, кадастровая карта) → **403 Forbidden**;
- `Referer: …/map?thematic=Default&zoom=17&baselayerid=235&active_layers=37581`
  (как шлёт браузер) → **200** и настоящий GeoJSON с MultiPolygon.

Значит: лимита не было, бана не было, ждать было нечего. Общий кадастровый
Referer годится для слоя участков (36048), но WAF отбивает им тематические
слои. Исправлено в 0.18.26 — запрос слоя несёт Referer со своим номером.

Два урока, оба дорогие:
- **чужую ошибку нельзя прятать под свой код**: `_land_fetch_json` сводил любой
  4xx к нашему 400, и «Forbidden» стало неотличимо от «неверный параметр».
  Пока текст источника не показали в ответе, диагноз был выдуман;
- **гипотезу проверяют прямым запросом, а не выкаткой**: один curl дал ответ
  за секунды, тогда как цикл «мерж → сборка 20 минут → деплой → проба» съел
  часы и трижды приносил старый образ.

Защита поставлена (0.18.23): предохранитель в `_nspd_getfeatureinfo` — пять
отказов подряд закрывают запросы слоёв на 15 минут (`NSPD_SCREEN_COOLDOWN`).
Бережёт не скрининг, а поиск участка: он живёт на той же НСПД, и разведка не
имеет права довести портал до жёсткой блокировки. Удачный ответ обнуляет счёт.

Номера добываются перебором с ядра: `GET /land/layer-sweep?cad=…&start=&end=`
опрашивает диапазон номеров по точке и возвращает ответившие слои с их
`categoryName`. Перебор находит слои, накрывающие ИМЕННО эту точку, поэтому
разведку гонять по нескольким характерным точкам (участок с ЗОУИТ; точка в
ООПТ/лесу у воды — напр. Серебряный Бор; точка на красной линии).

**Где НЕ искать номера слоёв (проверено 17.08.2026).** Два пути оказались
тупиковыми, повторять не нужно:
- *перебор номеров* — они не идут подряд: ЗОУИТ живут в 37577–81, а
  территориальные зоны уже 875838 (шестизначный). Перебор 37540–37599 дал
  54 «Internal Server Error» (номера не существуют) и 6 существующих — всю ту
  же семью ЗОУИТ. Шестизначное пространство перебирать бессмысленно;
- *entry-бандлы карты* (`/assets/hostInit-*.js`, `/assets/map-*.js`,
  `/assets/map/**`) — в них нет ни 37577, ни названий слоёв; размеры 0,1–60 КБ,
  это только точки входа, куски подгружаются динамически.

Остаётся правильный путь: список слоёв карта получает при старте — поймать
её первые XHR (открыть Network ДО загрузки карты и перезагрузить страницу),
либо снимать номер точечно, включая нужный слой и читая `active_layers` в
запросе (так добыты 37577 и 875838).

**Разведка слоёв закончена — имена не нужны (решение 18.08.2026).** Замечание
владельца: «мы опухнем это слои искать». Верно, и искать больше не надо:
`_NSPD_SCREEN_LAYERS` — просто список id из каталога, а ЧТО именно нашлось,
говорит сам ответ (`categoryName`, `type_zone`). Поэтому:
- сопоставлять номер с названием заранее не требуется вовсе;
- новый слой в каталоге достаточно добавить номером — он опознает себя сам;
- административная обвязка ПКК (субъекты, муниципалитеты, населённые пункты,
  кадастровое деление, охотугодья) отсеивается по имени — `_LAND_SCREEN_NOISE`;
- неверный номер отвечает Internal Server Error и просто пропускается.
Сбор ведёт `_land_screen_findings(lat, lng)`: опрашивает набор, отсеивает шум,
дедуплицирует по реестровому номеру и сразу классифицирует
(killer/economic/info).

есть. Механизм доказан: ручная сверка не нужна.

**Имена определяются автоматически, вручную сверять не нужно:** ответ каждого
слоя несёт `categoryName` и `type_zone`, поэтому проба (`screen-probe?layers=…`)
по подходящей точке сама скажет, какой номер чему соответствует. Осталось
прогнать кластер 875–879 по точке с лесом/водой/ООПТ и разложить имена.

**Отобранный набор слоёв для скрининга (из 17 доступных на НСПД, решение

- *красные флаги*: ЗОУИТ всех видов (охранные, СЗЗ, приаэродромные, природных
  территорий); Территориальные зоны (Ж/О/П); Красные линии; Особо охраняемые
  природные территории (ООПТ); Лесничества / граница лесопарка (лесной фонд —
  застройка запрещена); Береговые линии водных объектов (водоохранная/
  прибрежная); Территории объектов культурного наследия (сама территория
  памятника, не только буфер-ЗОУИТ);
- *полезный контекст (не флаг)*: участки, выставленные на аукцион / свободные
  от прав третьих лиц («доступен ли к покупке»); зоны социально-экономического
  развития (иногда льгота, не ограничение);
- *шум (не берём)*: единицы кадастрового деления, административные границы,
  тепловые карты, охотничьи угодья, комплексы объектов.
Все флаговые слои приходят одним identify — 17 галочек на карте нужны лишь
для просмотра, скрининг делает один серверный вызов.

## Роль Платона в скрининге: объясняет, но не считает (решение владельца, 17.08.2026)

Замечание владельца: «навряд ли он поймёт, сколько свободно под застройку, если
кругом красные линии и ЗОУИТ». Верно — и потому разделение жёсткое, как с
чувствительностью (числа считает движок, не модель):

- **движок считает факты и цифры**: какие ограничения пересекают участок,
  какой процент пятна съедает каждое, сколько метров остаётся под застройку,
  что killer, а что режет высоту. Геометрию модель не оценивает никогда —
  правдоподобный процент «на глаз» неотличим от посчитанного и потому опаснее
  отсутствия ответа;
- **Платон объясняет словами по готовым числам**: чем грозит эта зона, что
  значит третья подзона приаэродромной, почему в СЗЗ жильё запрещено. Он
  получает результат скрининга как данные (findings + проценты), а не сырые
  геометрии.

**База ограничений в основном приходит из ЕГРН, а не пишется нами.** Ответ НСПД
несёт `content_restrict_encumbrances` — текст ограничения для конкретной зоны,
плюс документ-основание (приказ, номер, дата, издатель). Это авторитетнее любой
сводной таблицы: ограничение цитируется по реестровой записи. Своя база нужна
только поверх — короткие пояснения по типам зон (что тип значит для девелопера)
и классификация killer/economic (`_LAND_SCREEN_CLASSES`). Пересказывать закон
своими словами там, где есть текст из реестра, не нужно.

## Оценка участка до финмодели — самостоятельный продукт (18.08.2026)

Задача владельца: к утру дать фишку, которую можно показывать брокерам —
оценка участка **в принципе, до всякой финансовой модели**.

Сделано: `GET /land/screening?cad=…` + блок на странице под карточкой участка.
Человек вводит кадастровый номер и сразу видит, что мешает строить: ЗОУИТ,
ООПТ, красные линии, тип территориальной зоны — с реестровым номером границы
и документом-основанием (приказ, номер, дата). Экономику запускать не нужно.

- флаги отсортированы по весу: **СТОП** (жильё запрещено) → **ВЛИЯЕТ** (режет
  пятно или высоту) → справка; цвет шапки блока следует худшему флагу;
- один участок — коротко, несколько — свод и разбивка по участкам;
- вывод **не разрешительный**: максимум «критических ограничений не
  обнаружено», всегда с оговоркой, что видно лишь внесённое в ЕГРН, а
  сервитуты, ГПЗУ и часть красных линий в реестре не отражаются;
- готовая оценка живёт 6 часов в кэше (`LAND_SCREENING_TTL`): каждый скрининг
  это два десятка запросов к НСПД;
- блок тихий — своя ошибка прячет его, но ничего не роняет: расчёт от него
  не зависит.

**Что покрыто и чего ещё нет (честно, 18.08.2026).** Опрашивается
`_NSPD_SCREEN_LAYERS`: пять подслоёв ЗОУИТ + кластер 875–879. Подтверждено
живыми ответами: ЗОУИТ всех видов (охранные, СЗЗ, приаэродромные), ООПТ
(875845), территориальные зоны (875838), красные линии (879243).
Пробел с лесом и водой закрыт **по построению** (0.18.35, замечание владельца

## 1. НСПД — основной многослойный источник
Работает: `https://nspd.gov.ru/api/aeggis/v3/{layer_id}/wms`, слой 36048
(ЗУ ЕГРН), GetMap и GetFeatureInfo, EPSG:3857, браузерные заголовки против WAF.
Существующую интеграцию не менять.

**Наблюдение владельца (17.08.2026): в дереве слоёв геопортала НСПД
(`nspd.gov.ru`) есть почти весь список для скрининга, и доступ тот же
открытый WMS, что мы уже используем.** Видны на карте (рендерятся): все
ЗОУИТ (объектов культурного наследия; энергетики, связи, транспорта;
природных территорий; охраняемых объектов и безопасности; иные ЗОУИТ),
«Территориальные зоны», «Красные линии», ООПТ, «Береговые линии (границы
водных объектов)», лесничества, зоны соц.-экон. развития, ОЭЗ. У каждого
слоя свой внутренний номер, как 36048 у участков.

Значение: большую часть «красных флагов» скрининга можно взять **из НСПД,
который уже подключён с ядра** — не воюя ни с SSO Москвы, ни с документной
моделью РГИС. Это самый дешёвый путь: инфраструктура доступа (WAF-заголовки,
TLS-фолбэк, EPSG:3857, `/land/map-probe`) готова.

**Честная граница (важно, не сюрприз потом): НСПД — это реестр ЕГРН.**
Он отдаёт то, что *внесено в реестр*:
- ЗОУИТ вносятся в ЕГРН → покрытие хорошее и авторитетное, это сильный
  источник ЗОУИТ для обоих регионов сразу;
- геометрия терр. зон и красных линий — только там, где зарегистрированы
  (полнота фрагментарна, см. раздел 4);
- **параметры застройки ПЗЗ (высота, плотность, % застройки, ВРИ) в ЕГРН
  НЕ хранятся** — они в муниципальных документах ПЗЗ. Поэтому НСПД даёт
  геометрию и код зоны (где внесены), но не параметры. За параметрами —
  ГИСОГД/РГИС (разделы 2–3) или локальная rule-base.

**Слой «Территориальные зоны» = зоны ПЗЗ (уточнение 17.08.2026).**
Территориальные зоны устанавливаются правилами землепользования и застройки,
поэтому этот слой НСПД и есть карта зонирования ПЗЗ: он отвечает на вопрос
«в какой зоне участок» и даёт её индекс/тип (Ж-1, О-1, П и т.п.) — уже
готовый флаг для скрининга (жилая / промзона / общественно-деловая).
Открытый вопрос — несёт ли слой числовой регламент (высота/%/плотность/ВРИ)
атрибутами или только индекс зоны + ссылку на документ ПЗЗ. Решается одним
`GetFeatureInfo` по слою с ядра. Если параметры там есть — региональные
порталы (разделы 2–3) для параметров не нужны; если только ссылка —
параметры из документа/rule-base. Это **первый тест** сессии реализации.

Следствие для реализации: первый шаг — **пробить номера этих слоёв в НСПД
с ядра** (`/land/map-probe` уже умеет) и проверить, что `GetFeatureInfo`
по каждому возвращает; распределить чеки: геометрия ограничений (ЗОУИТ,
ООПТ, вода, зоны) — НСПД; параметры застройки — региональные порталы/база.

ЗОУИТ: номера кандидатов 37577–37581 верны. Ключевое различие версий пути
(проба 17.08.2026): карта рисует тайлы через **GetMap на v4**
(`/api/aeggis/v4/37577/wms`, `/api/aeggis/v4/875838/wms`), а атрибуты берутся
через **GetFeatureInfo на v3** — v4 на GetFeatureInfo отвечает 502, v3 отдаёт
200 (пусто там, где объекта нет). Урок «22,5/25/35» сработал в обе стороны, и
ещё раз: пустой v3-ответ по 37577–81 был не «номер не тот», а «на московской
автостоянке ЗОУИТ нет» — и не «версия не та»: версия для опроса как раз v3.

**Развилка «атрибуты или только геометрия» закрыта фактом (17.08.2026):
НСПД по идентификации отдаёт пересекающие участок ЗОУИТ машинно.** Клик по
участку 50:20:0070312:8321 вернул «Найдено объектов: 3»: ЗОУИТ объектов
энергетики/связи/транспорта (2 шт., реестровые номера границ 50:00-6.2069 и
50:00-6.2068) + участок ЕГРН. Значит скрининг получает из НСПД: тип ЗОУИТ
(по имени слоя = красный флаг, напр. охранная зона энергетики), реестровый
номер границы и геометрию (для % накрытия). Параметров застройки в ЗОУИТ нет
by design — они и не нужны, ЗОУИТ это ограничение, а не зона с этажностью.
Пустой клик до этого был на месте без ЗОУИТ, а не признаком «слой картиночный».
Проба `screen-probe?cad=…` (ver=v3 по умолчанию) бьёт по центру участка тем
же GetFeatureInfo.

Слой конфигурации: `layer_id, logical_name, api_version,
expected_feature_type, last_verified_at, active` + health-check/canary.
Слой перестал отвечать → конкретная проверка UNAVAILABLE, расчёт не падает.
Запрещён вывод «ЗОУИТ отсутствует» из пустого ответа; правильный текст —
«В НСПД ограничение не обнаружено».

сборку на `(api|arcgis|geoserver|wms|wmts|tile|rest)`, затем живой

машинного анонимного доступа к карте/слоям пока нет. Для автоматизации

перспектива — собственная PostGIS-база подзон, обновляемая по официальным
изменениям ПЗЗ (ПП № 120-ПП и далее).

## 3. ПЗЗ Московской области
Решение пересмотрено владельцем 17.08.2026: РГИС МО
(`https://rgis.mosreg.ru`) — официальный публичный геопортал,
Мособлархитектура прямо указывает его как место просмотра утверждённых
ПЗЗ муниципалитетов. Поэтому для МО, как и для Москвы, **сначала
исследуем публичную карту, а не строим собственную базу из PDF**.
РГИС МО не считать закрытым или немашиночитаемым источником, пока не
проверены фактические browser-запросы. Прежняя формулировка «source =
local normalized PZZ database» остаётся только фолбэком на случай, если
проба покажет отсутствие машиночитаемого доступа.

**Итоги живой пробы (17.08.2026, Network в Safari + curl с ядра).**
Портал: `https://rgis.mosreg.ru`, SPA на Vue, карта — на `/v3`,
открывается **без авторизации** (вход — только для «Запросить сведения»
и т.п.). ПЗЗ публикуется как слои карты: поиск по слоям находит в группе
«МОСОБЛАРХИТЕКТУРА МО» слои «Правила землепользования и застройки (ПЗЗ)»
и «Территориальные зоны ПЗЗ».

Таблица фактических endpoint'ов (все проверены живым ответом):

| Назначение | Метод/URL | Доступ с ядра | Формат |
|---|---|---|---|
| Растровая подложка/слои | `GET /wmts/{слой}/{z}/{x}/{y}.png` (подложка `m10`) | **200 анонимно** (`image/png`, `ACAO: *`, кэш сутки) | PNG-тайлы |
| Векторные объекты слоя | `GET /v3/swagger/map/layer?SERVICE=GeoJSON&layer={id}&bbox={minLon,minLat,maxLon,maxLat}&zoom={z}` | **200 анонимно** (`application/json`) | GeoJSON FeatureCollection |
| Каталог WMTS | `GET /wmts?service=WMTS&request=GetCapabilities` | **401** (и с cookie) | — (закрыт) |
| identify по клику | открывает карточку «документ ИСОГД» (номер+дата) | — | документная ссылка |

Пример ответа GeoJSON (проба с ядра, `layer=193`,
`bbox=36.9709…,55.5371…,38.3978…,55.7216…`, `zoom=10`):

```json
{"type":"FeatureCollection","features":[
  {"type":"Feature","id":5195475750,
   "geometry":{"type":"MultiPolygon","coordinates":[[[[37.09804,55.57675], …]]]},
   "properties":{"feature_id":0,"label":"3889 14.11.2025","numberarea":13305288850}}
]}
```
25 объектов, ключи `type/id/geometry/properties`.

**Что это значит.** РГИС МО отдаёт слои как GeoJSON анонимно и с ядра —
машиночитаемый доступ есть. НО проверенный `layer=193` оказался **слоем
дел/документов ИСОГД**: в `properties` лежит номер документа с датой
(`label`) и `numberarea`, а кода зоны, ВРИ, высоты и % застройки там нет.
ПЗЗ на РГИС МО документо-ориентированы: зона ссылается на утверждающий
документ, а не выдаёт параметры атрибутами. Тот же ответ даёт identify по
клику (карточка «документ ИСОГД»).

**Осталось для сессии реализации (не блокирует MVP):**
- снять точный `layer={id}` слоёв «Территориальные зоны ПЗЗ» и «ПЗЗ»
  (включить именно их в дереве и прочитать `layer=` в Network) и
  проверить, несёт ли слой зон параметры атрибутами или только ссылку на
  документ; если только ссылку — параметры берём из документа/локальной
  rule-base, геометрию зоны — из GeoJSON;
- перечислить `layer={id}` остальных приоритетных слоёв (ЗОУИТ, ППТ,
  водоохранные, ООПТ, красные линии) — каждый включается на карте и даёт
  свой номер;
- проверить endpoint поиска по адресу/кадастру (в сборке был `/objects/search`).

Приоритетные слои: ПЗЗ (территориальные зоны), генеральный план,
ППТ/ПМТ, ЗОУИТ, приаэродромные территории, водоохранные зоны, ЗСО,
ООПТ, ОКН и зоны охраны, красные линии, инженерная инфраструктура.

По ПЗЗ отдельно проверить, что identify по точке возвращает: код
территориальной зоны, ВРИ, предельную высоту/этажность, максимальный %
застройки, плотность/коэффициент застройки, ссылку или ID утверждающего
документа. Результат пробы — таблица фактических endpoint'ов и пример
JSON-ответа по одному знакомому участку.

Найдётся стабильный слой ПЗЗ — источник МО оформляется адаптером
`PZZProvider`, как московский. Кандидат — не контракт, пока не
подтверждён живым ответом.

## 4. Красные линии
Hard-check не делать: стабильный слой не подтверждён, полнота внесения в ЕГРН
неизвестна, часть линий живёт в ППТ. Возможен только флаг RED_LINE_DETECTED;
отсутствие найденной линии НЕ означает отсутствия красных линий.
Кандидат-источник — раздел «Планировка территории города Москвы» ГИСОГД
(в `/chapters` — номер 7), проверяется той же пробой с ядра, что и ПЗЗ
(см. раздел 2).

## 5. Окружающая застройка
НСПД ОКС (этажность, если заполнена) + Overture Buildings, fallback —
OSM building:levels/height. Это не норматив — только информационный контекст.

## 6. Рельеф
Copernicus DEM GLO-30 как coarse screening. FABDEM в production не брать
(NC-лицензия). Вывод: «уклон участка ориентировочно X% — предварительная
оценка по DEM ~30 м, не вертикальная планировка».

## 7. Нормативы МО
Локальная rule-base по действующей редакции ПП МО № 713/30 + изменения,
включая № 774-ПП от 02.07.2026. Нормативы в runtime через LLM не искать.
Поля правила: `rule_id, territory, value, unit, rule_type, scope, area_basis,
conditions, effective_from, document, point_table, quote, official_source`.
Hard FAIL могут давать только MANDATORY_MINIMUM / MANDATORY_MAXIMUM;
RECOMMENDED — информационный warning.

## 8. Результат
Не один магический статус, а независимые чеки:
ЕГРН OK · ЗОУИТ WARNING · ПЗЗ UNAVAILABLE/OK/FAIL · парковки OK/FAIL ·
мин. территория РНГП OK/FAIL · красные линии DETECTED/NOT_DETECTED ·
рельеф INFO · окружающая этажность INFO.
Итог: CRITICAL / WARNING / NO_CRITICAL_FLAGS.
Запрещено «проект точно помещается»; максимум — «по автоматически
проверяемым ограничениям критических несоответствий не выявлено».

**Что пишет скрининг и что важно (решение владельца, 17.08.2026).** Числа
считает движок из данных, Платон их излагает и расставляет по важности — не
выдумывает и не выносит «подходит/не подходит». Три класса флагов по убыванию
веса:
- **killer** — запрещают жильё как таковое: СЗЗ и охранные ЗОУИТ (жильё в них
  запрещено), ООПТ, территориальная зона не под жильё. Первый гейт: не та
  зона — жилой расчёт бессмыслен.
- **экономические** — режут пятно и выход метров: **процент накрытия ЗОУИТ**
  (не «есть/нет», а сколько % пятна съедает — минус продаваемые метры → минус
  выручка), красные линии (территория общего пользования не застраивается),
  ограничение высоты (приаэродромные, зоны охраны ОКН) против нужной этажности.
- **информационные** — окружающая застройка, рельеф.

Ключевая величина, соединяющая скрининг с экономикой, — **% чистого пятна**
(участок минус ограничения): она идёт входом в финмодель, а не остаётся
справкой. Считается геометрией (пересечение контура участка с зоной). Самый
тяжёлый флаг поднимается в карточку решения рядом с финвердиктом.

**Один участок — кратко, группа — детально (решение владельца, 17.08.2026),
как с картой.** Один участок: 2–4 строки флагов. Группа (площадка из
нескольких участков): свод для территории целиком (что важно площадке, %
общей площади под ограничением) + разбивка по участкам (какой участок каким
ограничением задет и на сколько). Ограничения пространственные и у каждого
участка свои, поэтому разбивка обязательна. Данные те же — поиск уже
перебирает участки, скрининг гоняет по каждому свои `GetFeatureInfo`.

## 9. MVP (гипотеза владельца, подтверждена аудитом 16.08.2026)
1) кадастр + площадь (есть целиком); 2) ЗОУИТ НСПД (нужна проба слоёв);
3) парковки МО (движок уже считает — нужен только статус);
4) мин. территория РНГП МО (баланс уже считается — нужен только статус);
5) coarse slope (новый малый модуль); 6) ИЖС-окружение (готово) +
этажность ОКС (после пробы). Физика посадки (СПП → этажность/высота на
пятне) — INFO без внешних источников. ПЗЗ и красные линии — когда будет
надёжный источник. Пересечение геометрий в MVP — сеткой точек через готовый
GetFeatureInfo (без новых зависимостей); shapely/PostGIS — вместе со своей
базой ПЗЗ.

Места в интерфейсе: блок в «Участке» под карточкой участка; в отчёте раздел
«Реализуемость посадки» ПЕРЕД «Оценкой целесообразности покупки»; главный
флаг — в карточку решения.
