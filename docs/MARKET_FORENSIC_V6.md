# Ревизия модуля «Рынок и цена продаж»: диагноз и v6

Ответ на `docs/CLAUDE_MARKET_REVIEW.md`. Ревизия независимая: цепочка разобрана с
начала, каждая ошибка живого preview воспроизведена на коде, и только потом
принято решение, что оставить.

Ветка: `claude/market-search-v5-forensic-9068fn` (поверх `agent/market-search-v5`,
с влитым `main`). Production 8080 не тронут, PR #50 не мержится, golden fixture в
runtime не читается.

---

## 1. Диагноз: первопричины

Каждая воспроизведена скриптом на коде ветки, а не выведена из чтения.

### 1.1 Обзорная статья становилась жилым комплексом

`Москвы. Рейтинг застройщиков Дубая. Адрес офиса` — не сбой одного regex, а
следствие того, что **тип документа нигде не моделировался**. Извлечение шло по
склейке `title + snippet` любого документа. В `candidates_v5._phrase_names`
шаблон

```
(?:клубный\s+квартал|клубный\s+дом|жилой\s+квартал)\s+[«"']?([^|—–\n,]{2,60}?)…
```

имеет класс символов, который **допускает точку**. Ленивый захват идёт до первой
запятой, перескакивая границы предложений. Проза «…строим клубный дом в центре
Москвы. Рейтинг застройщиков Дубая. Адрес офиса, приходите» даёт ровно ту строку,
что видна на стенде. Проверено:

```
'в центре Москвы. Рейтинг застройщиков Дубая. Адрес офиса' | premium_residential_phrase
```

Второй слой той же причины: `_valid_name` проверял длину и «не адрес ли это», но
не имел ни грамматики названия, ни редакционного словаря. `Рейтинг застройщиков
Дубая` проходил все проверки.

### 1.2 Маркетинговый хвост в названии и расщепление одной страницы на две сущности

Набор терминаторов в шаблонах — `[—–|,:]` — **не содержит ASCII-дефиса**, а
агрегаторы пишут заголовки именно им: `ЖК Cult (Культ) - купить квартиру, цены`.
Захват доходил до запятой. Параллельно `_title_project_name` резал тот же
заголовок по другому правилу. Один документ давал два кандидата:

```
'Cult (Культ'                   | trusted_newbuild_project_page
'Cult (Культ) - купить квартиру'| explicit_residential_project
```

Ключи у них разные, поэтому дедупликация их не видела. Отсюда же `Тургенев -
купить квартиру` и `Мод` в одном списке.

### 1.3 Наследование subject-адреса и мнимые 0 км — главный дефект

`service.MarketDiscoveryService._geocode_project` строил подсказку адреса так:

```python
snippet = title + " " + snippet     # документа, из которого извлечено имя
address_hint = self._address_hint(snippet)
attempts = [address_hint, f"ЖК {name}, {locality}", f"{name}, {locality}"]
```

Поисковый сниппет почти всегда содержит слова запроса, а запрос — это адрес
объекта оценки (`новостройки рядом с "Москва, Саввинская набережная, 25"`).
Значит **любой** кандидат из такой выдачи забирал себе адрес Саввинской 25 и
вставал в ноль километров. Проверено:

```python
S._address_hint('Новостройки рядом с адресом Москва, Саввинская набережная, 25 — подборка ЖК Мод')
# -> 'Москва, Саввинская набережная, 25'
```

У этой же ошибки есть второй вход. Каталожная страница ЦИАН перечисляет несколько
ЖК в одном сниппете; все извлечённые из неё кандидаты получают **один и тот же**
адрес. Catalog-first из v5.1 поднял recall и одновременно умножил этот путь.

`service_v51._geocode_project` пытался лечить симптом: он звал `super()`, и если
результат в нужном городе — принимал. Москва совпадает всегда, поэтому
отравленная подсказка выигрывала до всех новых проверок.

Третий вход — точность геокодера. Ни `precision` от Яндекса, ни `addresstype` от
Nominatim не проверялись. Бренд, которого геокодер не знает, возвращает центр
Москвы (`precision: other`), а центр Москвы лежит внутри радиуса 5 км от многих
адресов. `Сидней Сити`, `Cult`, `Тургенев`, `Мод` — реальные московские проекты
из других районов, попавшие в выборку по одному из этих трёх путей.

### 1.4 Дубли одного ЖК

Ключ считался как `re.sub(r"[^a-zа-яё0-9]+", "", name.lower())` от **сырого**
названия. Следствия:

| написание | ключ v5 |
|---|---|
| `Savvin River Residence` | `savvinriverresidence` |
| `Саввин Ривер Резиденс` | `саввинриверрезиденс` |
| `Savvin River Residence - купить квартиру` | `savvinriverresidenceкупитьквартиру` |

Три сущности вместо одной: латиница и кириллица не сводились, маркетинговый хвост
входил в ключ. Идентификатор карточки агрегатора, который есть прямо в URL и
является жёстким якорем тождества, не использовался вообще.

### 1.5 Цена, не принадлежащая проекту

`MarketPriceEnricher.project_price` собирал числа из **любого** документа, где
`_mentions_project` нашёл название как подпоследовательность токенов. В районном
каталоге в одном сниппете идут цены пяти ЖК — все они уезжали одному. Требования
«документ — карточка этого проекта» не было.

### 1.6 Цена элитного проекта молча делилась на десять — не заявлено, найдено ревизией

```python
_PRICE_M2_RE = r"(?<!\d)(?P<value>\d{2,3}(?:[\s ]\d{3}){1,2}|\d{5,7}|…)"
```

Первая группа — минимум две цифры, групп по три — максимум две. Строка
`3 306 021 ₽/м²` (реальное число из golden dataset) не сопоставляется целиком:
совпадает хвост `306 021`. Результат проходит проверку диапазона `80 000 …
5 000 000` и выглядит правдоподобной ценой. Тот же шаблон копией лежал в
`official_price.py`, то есть официальная средняя ломалась так же. Это объясняет,
почему цены на стенде выглядели «неуверенными», а не явно неверными.

### 1.7 Экспозиция

`offers_count` брался как `max()` по всем срабатываниям `N квартир` во всех
документах — то есть максимум случайного числа из чужих сниппетов. Источника и
даты не было.

### 1.8 Рекомендация

`market_recommendation` принимала любой проект с `within_radius` и ценой. Мнимые
0 км и непривязанные цены входили в медиану наравне с настоящими аналогами.

### 1.9 Скрытая потеря

Кандидат, который не удалось геокодировать, отбрасывался через `continue`. Потеря
recall не была видна нигде. Виден был только тот мусор, что дошёл до конца.

## 3. Архитектура v6

```
документы -> тип документа -> кандидаты -> сущности ЖК
          -> адрес с доказательством -> координаты -> расстояние
          -> цена при доказанной привязке -> экспозиция -> рекомендация -> ответ
```

### `documents.py` — тип страницы

Разбор по URL, потом по тексту. Для ЦИАН, Яндекс Недвижимости, Домклика,
Новострой.ру и Наш.Дом.РФ адрес детерминирован, и из него же берётся **внешний
идентификатор** (`cian:4463213`, `yandex:3186893`, `novostroy:savvinskaya-27`) —
жёсткий якорь тождества. Типы: `project_page`, `catalog`, `listing`, `article`,
`developer_page`, `official_card`, `unknown`.

`article`, `listing`, `official_card` **не могут породить сущность проекта**.

### `normalize.py` — одно определение имени на модуль

Разделены три вещи, которые в v5 были одной строкой: показываемое имя,
канонический ключ и правило тождества.

* показ сохраняет брендовую вывеску («Клубный квартал Фрунзенский»);
* ключ снимает тип объекта, маркетинговый хвост, алфавит (транслит) и сводит
  номер очереди (`ДОМ XXII` = `Дом 22`);
* `same_project()` — единственное определение «это один проект»: похожесть ≥ 0,92
  **при равном номере очереди**. Номер обязателен: `Петровский парк` и
  `Петровский парк II` отличаются на два символа и иначе склеились бы, а это
  контроль 2.

Грамматика названия (`looks_like_project_name`) отклоняет обрывок прозы через
точку, незакрытую скобку, редакционный словарь (в том числе по префиксам, потому
что русский склоняет: «Хабаровск» есть в списке, «Хабаровска» — уже нет), голый
адрес, площадь, более шести слов и строку без признаков бренда.

### `candidates_v6.py` — кандидат появляется только структурно

* карточка проекта у агрегатора → имя из заголовка, уверенность 0,95, есть
  идентификатор;
* каталог или страница застройщика → только имя **в кавычках** или конструкция
  `ЖК X —`; уверенность ниже;
* каталожный кандидат помечается `address_attributable=False`.

Свободная проза названий не даёт вообще — это и закрывает класс 1.1.

### `entities.py` — сущность

Слияние по идентификатору агрегатора, затем по каноническому ключу, затем по
`same_project()` с защитой: **две разные карточки одного сайта — это два разных
проекта**, их сливать нельзя. После геокодирования — слияние по координатам
(< 250 м) вместе с похожестью имени; поглощённая вывеска приносит свои карточки,
иначе цена искалась бы по половине доказательств.

### `geo_resolution.py` — география с доказательством

1. подсказка, совпавшая с подписью subject-адреса, отбрасывается как `subject_echo`
   (`address_signature` сравнивает улицу и номер, игнорируя тип улицы и город);
2. подсказка берётся только из документа, приписанного этой сущности;
3. каталожный сниппет адресов не даёт;
4. если своего адреса нет — целевой поиск, и принимается только карточка **этого**
   проекта (совпал идентификатор или заголовок);
5. результат геокодера грубее уровня улицы отклоняется;
6. иначе `geo_unresolved` с причиной. Такой объект не получает расстояния, не
   попадает в выдачу и не участвует в рекомендации — он виден в `quarantine`.

### `price_evidence.py` — цена и экспозиция

Наблюдение принимается, если документ — карточка проекта **и** привязка доказана:
`external_id` (качество `high`) или совпадение заголовка (`medium`). Всё
остальное уходит в `rejected_observations` с причиной. Возвращаются
`price_per_sqm_min/median/avg/max`, `sample_count`, `sources`, `observed_at`,
`retrieved_at`, `quality`.

Экспозиция — отдельная структура `inventory` с `units / source / observed_at /
quality`. Нет надёжного числа — `units=None, quality="unknown"`.

### Рекомендация

Вход ужесточён: `within_radius` **и** `geo_status == resolved` **и**
`price_verified`. Ключ читается явно, без умолчания: отсутствующий `price_verified`
означает «не доказано». Сам алгоритм (MAD + веса) не тронут.

### Ответ API

`source.mode` = `forensic_entity_pipeline_v6`. Добавлены `quarantine`,
`quarantine_count`, `diagnostics.documents_by_kind`, `diagnostics.geo_unresolved`,
`diagnostics.outside_radius`. У каждого проекта — `address`, `address_source`,
`geo_status`, `price_verified`, `inventory`, `aliases`, `external_ids`,
`extraction_confidence`.

## 5. Экспозиция: что достижимо сейчас, а что требует провайдера

Прямой ответ на вопрос §11.8 брифа.

**Достижимо из поискового индекса (`quality: reported`/`low`)** — число лотов,
когда карточка проекта сама печатает его в сниппете («в продаже 3 квартиры»).
Покрытие неполное и нерегулярное: сниппет формирует поисковик, а не источник.
Годится как ориентир, не как учётная величина.

**Недостижимо без отдельного провайдера или парсера:**

* полная экспозиция застройщика по корпусам и очередям;
* суммарная экспозиция рынка в радиусе;
* динамика (темп продаж, вымывание) — нужен ряд наблюдений, а индекс даёт срез;
* структура по типам квартир и площадям.

Надёжные источники под это: проектные декларации и раскрытие ЕИСЖС по объектам
(данные о вводимых площадях и договорах), выгрузки агрегаторов по API, парсинг
карточек застройщика с фиксацией даты. Все три — отдельная работа с собственным
хранением истории, потому что показатель имеет смысл только в ряду.

До тех пор `inventory.quality` честно говорит `unknown`, и `null` не подменяется
числом из чужого сниппета.

## 6. Поверхности: панель, Платон, бот

Модуль перенесён в основную ветку и включён в рабочий entrypoint. Считает его
по-прежнему `service_v6`, но спрашивают теперь трое, и спрашивают одинаково.

`assessment.py` — единственный расчёт на все поверхности. Панель, инструмент
Платона `market_analogues` и команда бота `/market` зовут `assess()`, который
запускает конвейер один раз и приводит ответ к общему виду; формат у каждой
поверхности свой, числа — общие. Правило не декоративное: разъезд поверхностей
на одних данных в этом проекте случался дважды (PDF бота против отчёта сайта) и
оба раза выглядел безупречно с обеих сторон.

Своей арифметики в `assessment` нет — по той же причине, по которой её нет в
адаптере результата v2. Цену считает `recommendation.py`; здесь она только
пересчитывается в единицы поля «Цена квартир» и называется своим основанием:
`price_per_sqm` — ₽/м², `price_th_per_sqm` — тыс. ₽/м².

Основание цены переносится на поверхности целиком. Средняя ЕИСЖС — среднее по
зарегистрированным сделкам, и кнопки «применить в модель» у неё нет ни на
странице, ни в боте: подпись под кнопкой предупреждения не удержит, а
применённое число потом неотличимо от посчитанного по рынку.

Порядок установки в `main_registry` — часть работы, а не оформление. Слой
перестройки снимает копию `core.PAGE` при установке, поэтому панель ставится до
него; иначе вкладки нет ни на основном интерфейсе, ни на `/classic`, и снаружи
это неотличимо от невыкаченного модуля. Проверяется тестом
`tests/test_market_reaches_every_surface.py` — он падает на переставленных
строках.

2. Новый UI — только после приёмки, как и требует бриф. Сейчас панель приведена к
   контракту v6 и показывает адрес проекта, качество цены, экспозицию и карантин;
   компактная таблица с KPI — следующая итерация.
3. Экспозиция как учётная величина требует отдельного провайдера (§5); до тех пор
   `inventory.quality` говорит `unknown`, и число из чужого сниппета его не
   подменяет.
4. Ступенчатая специальная ставка и прочие открытые вопросы модуля рынка к этой
   ревизии не относятся.
