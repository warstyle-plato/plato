# Утверждённые версии ГПР

Первый утверждённый ГПР по-прежнему загружается один раз через
`/monitor/schedule`. Обычная загрузка ГПР-факта не утверждает и не заменяет план.

Для существующего проекта в «Данных проекта» выбирают файл и дату начала
действия, затем нажимают «Проверить новую версию плана». Предварительный просмотр
показывает проект, дату и число работ. Кнопка «Утвердить новую версию» применяет
только проверенные байты к той версии, на основании которой был открыт просмотр.
Если другой запрос уже изменил план, требуется повторный просмотр.

Новая версия действует с сегодняшней или будущей даты. Архивные срезы сохраняют
свой источник для доказательства факта. При утверждённом плане оставшихся работ
обычный экран показывает единственный действующий план вместе с фактами выбранной
даты: [рабочий план и история факта](remaining_work_plan.md).
Дата показания процента в корпусном ГПР остаётся датой его шапки;
дата утверждения не превращается в дату выполнения работ.
Работа, у которой в утверждённом ГПР нет понятной даты начала или окончания
(«31.06.2027», пустая ячейка, окончание раньше начала), не уходит из графика молча:
над графиком Монитора она названа с корпусом, разделом и ячейкой файла
(`schedule.undated_works`, один помощник `developaid_monitor._undated_works`).

Исходный `baseline/gpr.xlsx` и прежние ручные решения не перезаписываются.
Новые оригиналы хранятся по SHA в `baseline/schedule_sources`, а атомарный журнал
`baseline/schedule_versions.json` содержит цепочку версий, дату начала действия
и время утверждения. При чтении проверяются цепочка и отпечаток выбранного файла.
Общая файловая блокировка защищает от одновременного утверждения двух версий.

ГПР-факт и точечные проценты новых версий привязаны к отпечатку плана.
Старые записи без отпечатка остаются свидетельствами первоначального плана,
только если на дату показания ещё действовала его начальная версия. Неизвестное
происхождение после смены версии не восстанавливается догадкой по старому файлу.
Совпадение одного идентификатора работы не переносит ГПР-факт и проценты в
другую версию.

Привязки накопительных КС к работам переносятся на новую версию только для
работ с тем же определением: код, название, объект, раздел и WBS
(`gpr_physical.definition`); плановые даты могут отличаться. Переносится
последнее решение по прежней версии вместе с правилами проверки; явное снятие
привязки ничего не переносит. Перенос выполняется только при чтении и ничего не
записывает: экран показывает «Привязки N работ перенесены…», а закрепляет их за
новой версией обычное сохранение. Переименованная, перенесённая в другой
объект или раздел и исчезнувшая работа не переносится; её называют в
`binding_not_carried` с причиной, и её привязывают заново. Если сменился и архив
накопительных, перенос проходит через ту же проверку позиций, что и смена архива.
Завершённая работа, подтверждённая в двух версиях с одним определением,
считается одним фактом; поздний частичный факт по ней в другой версии снимает
прежние сто процентов. Прежний журнал связей КС не перезаписывается.

При объединении проектов факты соединяются только при доказанном одинаковом
источнике. Несовместимые и неизвестные источники сохраняются в архиве конфликтов,
без присвоения им отпечатка основного плана. Уже выбранные ГПР, метаданные и
журнал версий основного проекта не подменяются журналом другого проекта.

Оба API (`/monitor/schedule/version-preview` и
`/monitor/schedule/version-approve`) требуют текущий ключ администратора до
чтения источников. Утверждение проверяет `expected_previous_sha256` и
`expected_source_sha256`. Ответы, включая отказы, не кэшируются. Каждый запрос
читает общий журнал с диска; внутри одного чтения выбор источника фиксирован,
чтобы одновременное утверждение не смешало план и факт разных версий.

Проверки: `tests/test_schedule_approved_revisions.py`. Реальные частные ГПР и
результаты предметной приёмки в репозиторий не включаются.
