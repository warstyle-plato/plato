# Споры и претензии: один спор — одна карточка

Владелец (23.10.2026): «по судам и спорам для сводки надо аудит провести, все
перепутано в одну кучу везде, и тяжеловесная очень структура карточки, надо
текущий статус только. А там Арктик перепутан с КИМАКГ». Код —
`developaid_legal_cases.py`, страница — `developaid_report_page.py` (карточка
«Споры и претензии» на `/report`), маршруты `/monitor/legal*` в
`engine/monitor.py` (только команде), вывод — `developaid_management_report.py`
(`_legal_html`, `_legal_lines`, «Главное»). Образцы:
`docs/samples/legal_light_card_sample.html`,
`docs/samples/report_legal_cards_to_check.png`,
`docs/samples/report_legal_current_status.png`.

## Аудит: откуда бралась путаница

Откуда поля: контрагент, дело, предмет, стадия, требования (суммы с
направлением) и хронология — из карточки, которую Платон составляет по
документам (`draft`, строгая схема `CASE_SCHEMA`), человек правит и
подтверждает (`save`); готовые карточки приходят файлом (`import_cards`) или
со стартовым файлом на сервере (`ensure_seed`). Суммы в сводке — `totals`
(сложение требований по направлению).

Где данные одного спора попадали в другой:

1. **Одна карточка на пачку документов.** Схема допускала одного контрагента;
   письма двух споров в одной загрузке сливались в одну карточку.
2. **«Дополнить» склеивало.** Платон получал действующую карточку и указание
   «обнови её» — документы другого спора дописывались в неё; список документов
   при сохранении только рос, правка руками его не очищала.
3. **Импорт сравнивал текст имени.** Ключ «контрагент + договор + дело»:
   «ООО «Арктик»» и «Арктик» — два спора; правка номера дела в файле давала
   вторую карточку; полное совпадение ключа пропускало строку, и исправление
   из файла не доходило никогда.
4. **Переименование не замечалось.** Карточка одного контрагента могла
   продолжиться под другим именем со всей прежней историей.
5. **Сводка тяжёлая.** По каждому спору — требования по пунктам, хронология,
   следующий шаг, позиция; два спора с одним контрагентом в «Главном» не
   различались.

## Правила

- Карточка обновляется только по её `id`: из формы «Изменить», из файла
  (поле `id`, его даёт выгрузка `export_cards`) или по ответу владельца на
  вопрос импорта (`decisions`). Имя, договор, позиция строки соответствия не
  задают.
- Строка файла без `id`: совпала с карточкой до буквы — пропуск (повторная
  загрузка); тот же контрагент или тот же номер дела — вопрос с кнопками
  «Обновить карточку …» / «Внести новым спором»; иначе — новая карточка.
- Платон пишет в карточку ровно один спор; другой контрагент или другое дело
  из тех же документов — в `other_disputes`, страница называет их
  предупреждением. Если при «Дополнить» Платон назвал другого контрагента —
  тоже предупреждение.
- Уже смешанные карточки не правятся сами. `suspicions` собирает признаки
  (два номера дела, два контрагента в поле, контрагент другой карточки в
  тексте, общий номер дела с другой карточкой, смена контрагента в истории,
  «суд» без инстанции) в список «Проверьте эти карточки» с кнопками:
  «Разнести на две карточки» (`split`: отмеченные требования, события и
  документы уходят в новую или существующую карточку, номер дела — вместе с
  ними; обе — новыми версиями журнала), «Это один спор» (`acknowledge`,
  `legal/reviewed.json`), «Указать стадию». Совпадение имён здесь — повод
  спросить, а не склеить.
- Стадии — семь (`STAGES`): претензия, переговоры, суд первой инстанции,
  апелляция, кассация, исполнение, закрыт. Прежнее «Суд» (`court`) читается
  как «Суд, инстанция не указана» и стоит в списке на проверку, пока
  инстанцию не укажут; новой не выбирается и «одним спором» не снимается.
- Карточка на странице — контрагент, стадия, сумма, предмет одной строкой,
  ближайшая дата, номер дела; договор, требования по пунктам, хронология,
  позиция, документы и версии — в свёрнутых «Подробностях».
- Сводка, PDF и сообщение — только текущий статус: контрагент (и дело),
  предмет, стадия, ближайшая дата, сумма с направлением («наши требования» /
  «требования к нам», в обе стороны — два числа).
