# DevelopAid v0.17.26 — ТЭП считает сам калькулятор ГлавАПУ

## Что изменилось

Копировать методику ГлавАПУ оказалось тупиком: за сутки плата за ВРИ разошлась
со штатным калькулятором на 1,75%, компенсация за соцобъекты — на 19%, и оба
раза расхождение находил человек на скриншотах. Теперь сервер запускает
настоящий калькулятор браузером без экрана и повторяет ту же последовательность,
что отрабатывает скрытый iframe на сайте. Наши формулы остались фолбэком.

## Как включить на ядре (Yandex Cloud)

Chromium ставится в образ — в `python:3.11-slim` нет ни браузера, ни системных
библиотек к нему. Образ тяжелеет примерно на 500 МБ.

```bash
cd plato
git pull
# в .env добавить строку:  GLAVAPU_HEADLESS=1
docker compose build          # соберёт образ вместе с Chromium
docker compose up -d
```

Собрать без браузера (расчёт останется на формулах, как до перехода):

```bash
docker compose build --build-arg INSTALL_BROWSER=0
```

## Как проверить, что работает

```bash
curl -s http://127.0.0.1:8080/telegram/status | python3 -m json.tool | grep -A6 glavapu_headless
```

- `enabled: true` — переключатель включён;
- `runs` растёт после каждого расчёта по кадастровому номеру;
- `fallbacks` растёт, когда калькулятор не отдал таблицу и расчёт ушёл в формулы;
- `last_error` — причина последнего отката.

Живая проверка: посчитайте в боте участок, по которому расходились числа, и
сравните соцплатёж с расчётом на сайте — они должны совпасть.

## Если пойдут откаты

Смотреть `last_error`. Частые причины: с ядра не открывается `genplan.tech`
(сетевые правила Yandex Cloud), не хватает памяти на Chromium (300–400 МБ на
запуск, а воркеров два), изменилась вёрстка калькулятора. Пока откаты идут,
бот считает как раньше и честно пишет в отчёте, что расчёт запасной, —
выключать ничего не нужно, но и числа ГлавАПУ до починки не приедут.

Возврат к прежнему поведению — одна строка в `.env`: `GLAVAPU_HEADLESS=0`
и `docker compose up -d`. Пересборка не нужна.

# DevelopAid v0.12.64 — участок определяется положительно, а не перебором исключений

## Что изменено в v0.12.64

В прошлой версии я убирал из поиска по адресу помещения — перечислял слова «помещ», «квартир», «машино-мест». Подход неверный: ЕГРН заводит десятки видов объектов, и любой невнесённый в список просачивается в выдачу. Правильно от обратного — показывать только то, что **положительно опознано как земельный участок**.

### Опознание участка

Категория объекта из ответа НСПД проверяется на «участ», «земел», «зу». Всё остальное участком не считается.

Отдельно убран опасный запасной путь. Раньше было так:

```python
if _nspd_value(options, "category") or "land_record_area" in options:
    return "land"
```

Любой объект с площадью становился участком. «Объект незавершённого строительства» и «Единый недвижимый комплекс» попадали в земельные участки и **увеличивали площадь территории**, а от неё считается всё остальное.

Теперь: если категория названа, решает она. Незнакомая категория — это `«Объект ЕГРН»`, а не участок. По полям судим только когда категории нет вовсе.

| Категория НСПД | Вид |
| --- | --- |
| Земельные участки | участок |
| Помещения, Машино-места, Квартиры | помещение |
| Здания, Сооружения, Объекты незавершённого строительства, Единый недвижимый комплекс | ОКС |
| что-то новое | объект ЕГРН, в участки не попадёт |

### Что видно в выдаче

Поиск по адресу и по координатам оставляет только участки. Скрытое считается по видам и объясняется:

> Показаны только земельные участки. Скрыто объектов: 147 (помещение — 143, объект капитального строительства — 4). Для расчёта проекта нужен участок; чтобы увидеть конкретный объект, введите его кадастровый номер.

Поиск по кадастровому номеру фильтр не применяет: спросили конкретный объект — получите его. Флаг `include_premises` снимает фильтр и для адреса.

В ответе вместо `hidden_premises` теперь `hidden` с разбивкой по видам и `hidden_count`.

Версия приложения, `/health`, заголовок страницы, User-Agent и версия бота обновлены до `0.12.64`.

# DevelopAid v0.12.63 — по адресу возвращается участок, а не список квартир

## Что изменено в v0.12.63

Поиск по адресу заработал на живом НСПД — и сразу выяснилось, что он возвращает **все объекты недвижимости по адресу**: квартиры, машино-места, кладовые. По жилому дому это сотни записей, среди которых нужный земельный участок теряется.

Причина в классификаторе: помещения попадали в ту же корзину, что и здания.

```python
if any(word in label for word in ("здан", "сооруж", "помещ", ...)):
    return "building"
```

«Помещ» стояло в одном списке со «здан» — квартира и жилой дом становились одним и тем же «объектом капитального строительства».

### Что сделано

Появился отдельный вид объекта — **помещение**: квартиры, машино-места, комнаты, доли в праве. Проверяется раньше здания, иначе «помещение в здании» уезжает в ОКС.

Поиск **по адресу и по координатам** помещения не показывает: там нужен участок. Но не молча — в предупреждениях сказано, сколько скрыто и как их увидеть:

> По этому адресу в ЕГРН 143 помещений — квартиры, машино-места, кладовые. В выдаче они скрыты: для расчёта проекта нужен земельный участок. Чтобы увидеть помещение, введите его кадастровый номер.

Поиск **по кадастровому номеру** отдаёт ровно то, что спросили. Запросили квартиру — получите квартиру: прятать ответ на прямой вопрос нельзя.

Ответ получил поле `hidden_premises`, а запрос — флаг `include_premises` на случай, когда помещения нужны.

Порядок выдачи прежний: сначала земельные участки, потом здания.

Версия приложения, `/health`, заголовок страницы, User-Agent и версия бота обновлены до `0.12.63`.

# DevelopAid v0.12.62 — берутся все участки, а не первые десять

## Что изменено в v0.12.62

Из 22 кадастровых номеров в расчёт попадали **первые десять**. Территория выходила 16 га вместо 22,4 га, и от заниженной площади считалось всё: площадь квартир, население, социальные объекты, плата за смену ВРИ, вся экономика.

Причин было две, и обе мои.

**Лимит 10.** Константа `_LAND_LOOKUP_MAX_RESULTS` стояла равной десяти, хотя на самой странице написано «за один запрос — до 30 участков». Поднято до 30, вынесено в переменную окружения `LAND_LOOKUP_MAX_RESULTS`. Блок Московской области теперь и запрашивает 30 явно.

**Обрезка молчала.** Список просто резался `numbers[:limit]` без единого слова. Теперь при обрезке выдаётся предупреждение, где сказано и сколько номеров пришло, и сколько обработано, и главное — что площадь занижена:

> В запросе 22 кадастровых номеров, обработаны первые 10. Площадь территории и все расчёты от неё занижены — разбейте запрос на части.

### Скорость

Номера опрашивались у НСПД по одному. Тридцать последовательных запросов — это минуты ожидания, а на тайм-ауте шлюза расчёт и вовсе не дошёл бы. Опрос стал параллельным, три потока: больше портал начинает придерживать. Порядок участков сохраняется, результат совпадает с последовательным опросом. Число потоков меняется переменной `LAND_LOOKUP_WORKERS`.

# DevelopAid v0.12.59 — пошаговая инструкция в боте

## Что изменено в v0.12.59

Справка `/help` состояла из четырёх абзацев и обходила главное: пользователь не понимал, что будет с его участком и почему. Она предлагала «отправьте кадастровые номера московского участка», а про Московскую область и остальные регионы не говорила ничего — при том что методики у них разные.

Теперь инструкция построена вокруг трёх случаев и объясняет, чем они отличаются.

| Территория | Как считается |
| --- | --- |
| **Москва**, включая Троицкий и Новомосковский округа | нормативные ТЭП по калькулятору ГлавАПУ |
| **Московская область** | нормативы РНГП МО; плата за смену ВРИ по УПКС кадастрового квартала и распоряжению № 114-Р |
| **Другой регион** | сведения ЕГРН по участку, ТЭП вводится экспертно — ответами на вопросы бота или через Excel-шаблон |

Отдельно оговорено, что кадастровый номер `50:*` не означает область: у Троицкого и Новомосковского округов номера тоже начинаются с 50, и считаются они по московским правилам. Это ровно та ошибка, которую мы чинили в 0.12.49, и пользователю о ней знать полезно.

Инструкция стала пошаговой:

1. отправить участок — номер, несколько номеров, адрес или координаты;
2. бот определяет территорию и методику;
3. проверить карточку и открыть мини-приложение;
4. забрать карточку, PDF и ZIP с моделью — с пояснением, что `00_Модель` пересчитывается при правке вводной, а `90_Детализация` нет;
5. спросить Платона.

Короткая справка по кнопке «Что умеет DevelopAid» тоже перестала быть общим списком возможностей: она называет три случая и отправляет за подробностями в `/help`.

# DevelopAid v0.12.58 — достроены первые месяцы рассрочки ВРИ

## Что изменено в v0.12.58

На листе «ЗУ» блок рассрочки ВРИ считает правильно начиная с третьей колонки. В первых двух колонках шаблона были пропуски:

| Ячейка | Было | Чем это оборачивалось |
| --- | --- | --- |
| `D65` окончательный платёж | `='Расчет ВРИ (ТЭП)'!D73` | статика: вся плата падала в **первый месяц модели** независимо от дат |
| `E65` | пусто | платёж во втором месяце не срабатывал |
| `D66`, `E66` проценты | пусто | первые два месяца проценты на остаток не начислялись |

С колонки `F` формулы верные: `=IF(F19=$C$63, ...)` для окончательного платежа и `=IF(F19>=$C$62, ($C$60−выплачено)×F61/12, 0)` для процентов. Теперь эти же формулы достроены для `D` и `E` с поправкой на отсутствие предыдущих колонок.

Особенно это важно для единовременной оплаты: у неё «Первый» и «Последний» совпадают, строка 64 не срабатывает по построению, и весь платёж проводится строкой 65 — то есть ровно той, что была задана статикой.

Формул в книге стало 113 709: две заменены датами окна рассрочки, три недостающие достроены.

## Как отличить старую выгрузку от новой

Откройте лист «ЗУ» и посмотрите строку 64 «В месяц»:

- **`700`** при плате 50 372 — это `C60/(12×6)` из шаблона, значит лист не заполнялся: выгрузка сделана сборкой до 0.12.53;
- **`=C60/1`** для единовременной или `=C60/69` для шестилетней рассрочки — лист заполнен.

Второй признак: строка 61 «%% за рассрочку». `0%` — старая выгрузка, `3%` — новая.

# DevelopAid v0.12.57 — Кср определяется округом, а не вводится руками

## Что изменено в v0.12.57

В блоке параметров Московской области поле «Средняя цена м², Кср» было обычным вводом и стояло пустым до первого расчёта. Это неправильно: Кср не выбирают, он определён распоряжением № 114-Р по муниципальному образованию.

Причина была в эндпоинте: `/mo/reference` отдавал по округам только УПКС, а Кср — лишь общие сведения о справочнике (количество строк, среднее по области, период). Показать цену выбранного округа до расчёта интерфейс просто не мог.

### Что сделано

`/mo/reference` теперь отдаёт по каждому из 60 округов `market_price_rub_per_sqm` и `market_price_basis` — по округу цена из распоряжения или, если округа в нём нет, среднее по области.

Поле Кср стало справочным: только для чтения, заполняется сразу при выборе округа, подпись показывает основание.

| Округ | Кср | Подпись |
| --- | --- | --- |
| Городской округ Мытищи | 238 052 | по округу, распоряжение 114-Р |
| Богородский городской округ | 131 783 | по округу, распоряжение 114-Р |
| Городской округ Серебряные Пруды | 77 041 | по округу, распоряжение 114-Р |
| округ не выбран | — | определится по округу участка |

Ручной ввод остался, но стал осознанным исключением: галочка «задать вручную» снимает блокировку, подпись меняется на «задано вручную, справочник не применяется», и введённое значение переживает смену округа. Снимите галочку — вернётся справочное.

В расчёт цена уходит только при включённой галочке. В остальных случаях на сервер отправляется ноль, и Кср подставляет сам сервер по округу: одна точка истины вместо двух.

Версия приложения, `/health`, заголовок страницы, User-Agent и версия бота обновлены до `0.12.57`.

# DevelopAid v0.12.56 — сведение с 0.12.55 и возврат к читаемым исходникам

## Что изменено в v0.12.56

В `main` появилась сборка 0.12.55, где `main.py` запускал приложение так:

Код исполнялся из base64-блоба, а поверх него патч-модуль на лету подменял функции ядра. В таком виде изменения не видны в diff, не находятся поиском по репозиторию и не воспроизводятся из исходников.

Блоб распакован и сверен: **это ровно наш `main.py`, отличие — одна строка с номером версии**. Терять там нечего, поэтому `main_wrapper_01255_payload.py` и `release_01255_patch.py` удалены, а `main.py` вернулся к обычному виду.

**Формулировки об оценочном характере даты** в списке режимов, подписи поля и пояснении на вкладке ВРИ.

# DevelopAid v0.12.49 — Новая Москва, транспорт НСПД и паритет по ВРИ

## Что изменено в v0.12.49

Перенесено из сторонней линии `platomain_3` — это то, что там было сделано правильнее нашей ветки.

### Новая Москва больше не уезжает в областной расчёт

Было: кадастровый номер `50:*` уходил в калькулятор Московской области по одному префиксу.

```python
if numbers and all(str(number).startswith("50:") for number in numbers):
    _telegram_handle_mo_numbers(chat_id, numbers)
```

**Это ошибка: у Новой Москвы кадастры тоже начинаются с 50.** Троицкий и Новомосковский округа — это Москва, считать их по нормативам области нельзя.

Стало: сначала спрашиваем ГлавАПУ, и решение принимает отдельная функция `cadastral_route(numbers, analysis)`:

| Номера | ГлавАПУ | Куда |
| --- | --- | --- |
| `50:*` | территория московская | Москва |
| `50:*` | территория не московская | Московская область |
| `50:*` | не ответил | Московская область |
| `77:*` | территория московская | Москва |
| `77:*` | не ответил | ошибка |
| `50:*` + `77:*` | не московская | Москва (областной расчёт неприменим) |

Функция чистая — решение проверяется тестами без обращения к сети.

### Транспорт НСПД

Портал отвечает не всякому клиенту: без браузерных заголовков он молча отдаёт пустой результат. К запросам на `nspd.gov.ru` добавлены `Referer`, `Origin` и браузерный `User-Agent`; в поисковый запрос добавлен `CRS=EPSG:4326`. На другие хосты заголовки не ставятся.

Сертификат НСПД выпущен национальным удостоверяющим центром, которого нет в стандартном хранилище доверия большинства хостов. Проверка сертификата **не отключена по умолчанию**: первый запрос идёт обычным путём, и только если цепочка не проверилась, делается один повтор без проверки — для этого хоста и с отметкой в `/land/providers`:

```json
"nspd_tls": {"fallback_allowed": true, "verification_disabled": true}
```

`verification_disabled: true` означает, что на хосте не установлен корневой сертификат Минцифры. Запасной путь целиком выключается переменной `NSPD_TLS_FALLBACK=0`. Обычные сетевые сбои повторно без проверки не отправляются.

### Поля ЕГРН

Список синонимов площади расширен ключами, которые портал начал отдавать без предупреждения: `area_value_m2`, `area_sqm`, `square`, `params_area`, `areaValue`.

### Паритет по ВРИ со сторонней линией

Сверка маршрутов и параметров показала два пробела против линии `platomain_3`. Оба закрыты.

**Дата возникновения обязательства** перестала быть жёстко привязанной к РнС. Соглашение о смене ВРИ подписывается до получения разрешения, а платёж до открытия ПФ несёт БРИДЖ, а не ПФ, — поэтому сдвиг даты меняет пик БРИДЖа и выбирать режим надо осознанно:

| `vri_obligation_date_mode` | Дата |
| --- | --- |
| `at_rns` (по умолчанию) | в дату РнС |
| `before_rns_1m` | за месяц до РнС |
| `before_rns_3m` | за три месяца до РнС |
| `after_purchase` | через `vri_months_after_purchase` мес. после покупки |
| `manual` | из `vri_obligation_date` |

Каждая дата отдаёт пояснение и признак «оценочная»: точной считается только введённая вручную. Пояснение видно в карточке ВРИ и на листе «ВРИ». Умолчание оставлено прежним — `at_rns`, чтобы уже посчитанные модели не поехали.

**Первый взнос по рассрочке** — `vri_initial_pct`. Платится в дату обязательства, остаток дробится на регулярные платежи графика и, соответственно, снижает проценты на остаток. По умолчанию 0: подставлять чужой процент как норматив мы не будем.

### Удалён стартовый хотфикс

# DevelopAid v0.12.48 — льгота по ВРИ и диаграммы в выгрузке модели

## Что добавлено в v0.12.48

Обе доработки взяты из стороннего архива `platomain_3.zip` — это единственное, что там было сильнее нашей ветки.

### Льгота по плате за ВРИ

Обязательство может быть уменьшено решением города — например, при строительстве социальных объектов за свой счёт. Появились три параметра:

| Параметр | Значение |
| --- | --- |
| `vri_relief_mode` | `none` / `percent` / `amount` |
| `vri_relief_pct` | доля от суммы обязательства, % |
| `vri_relief_mln` | фиксированная сумма, млн ₽ |

Льгота срезается **до** всего остального: от суммы к оплате считаются и резерв в накладных, и график рассрочки, и проценты на остаток. При льготе 30% на обязательство 3 млрд проценты по шестилетней рассрочке падают с 1 125,2 до 787,6 млн ₽ ровно пропорционально. Льгота больше обязательства обнуляет его, блок ВРИ при этом выключается.

При очерёдности льгота применяется один раз — в базовом расчёте, из которого берётся доля очереди; повторно к доле она не срезается.

В карточке ВРИ и на листе «ВРИ» появились строки «Обязательство до льготы» и «Льгота» — они показываются только когда льгота есть. В структуру расходов льгота не попадает: это не расход, а несостоявшийся расход, и строка «Смена ВРИ / земельные права» уже показывает сумму к оплате.

Собственный XLSX-писатель научился строить диаграммы — без внешних библиотек, нативными частями пакета (`xl/charts`, `xl/drawings`):

- **«Расходы»** — столбики структуры полных расходов;
- **«Помесячно»** — линии остатка ПФ, эскроу и остатка БРИДЖ;
- **«Сравнение очередей»** — LLCR по очередям и выручка против CAPEX.

Диаграммы ссылаются на диапазоны листов формулами, а не на копии чисел: правка ячейки перерисовывает график. Живые формулы итогов при этом никуда не делись.

# DevelopAid v0.12.47 — плата за изменение ВРИ стала графиком, а не разовым расходом

## Что изменено в v0.12.47

Плата за смену ВРИ раньше падала одной суммой на дату РнС. Это удобная, но неверная заглушка: обязательство возникает по соглашению, может гаситься рассрочкой с процентами на остаток и делиться между БРИДЖем, ПФ и собственным капиталом. От этого зависят размер бриджа, собственный капитал до ПФ, даты возникновения расходов, стоимость рассрочки, проценты, потребность в лимите ПФ и, следом, NPV, IRR и LLCR.

Теперь ВРИ — отдельный блок модели с собственным графиком.

### Вводные

Появилась группа «Смена ВРИ и земельные права»:

| Параметр | Значение |
| --- | --- |
| `vri_required` | требуется ли изменение ВРИ |
| `vri_region` | Москва / Московская область |
| `land_right` | собственность / аренда |
| `vri_obligation_date` | дата возникновения обязательства (пусто — РнС) |
| `vri_payment_mode` | единовременно / рассрочка |
| `vri_installment_years`, `vri_periodicity_months` | срок и периодичность |
| `vri_schedule_mode` | автоматический / ручной график |
| `vri_interest_enabled`, `vri_interest_spread_pp` | проценты на остаток и спред |
| `vri_early_repay_after_pf` | досрочное погашение остатка после открытия ПФ |
| `vri_pf_open_date` | дата открытия ПФ (пусто — РнС) |
| `vri_in_bank_budget` | включена ли ВРИ в банковский бюджет |
| `vri_financing_mode`, `vri_share_bridge_pct`, `vri_share_pf_pct`, `vri_share_equity_pct` | источники оплаты |
| `vri_security_cost_mln` | расходы на обеспечение обязательства |

Ручной график задаётся списком `vri_manual_schedule` — датами и суммами основного долга; расхождение с суммой обязательства попадает в предупреждения, а не втихую меняет расчёт.

### Москва

Рассрочка на 1, 3 или 6 лет, квартальные платежи, проценты на остаток по ключевой ставке плюс 3 п.п. Введённый срок вне трёх допустимых приводится к ближайшему. Остаток можно погасить досрочно после открытия ПФ.

### Московская область

Рассрочка зависит от суммы обязательства, периодичность своя, проценты автоматически не начисляются — только если это прямо предусмотрено соглашением; при включённых процентах модель об этом предупреждает. Официальные диапазоны сумм в код не зашиты: их задаёт `vri_mo_ranges` списком `{"limit_mln": …, "years": …, "periodicity_months": …}`, последняя строка без `limit_mln` работает как «свыше». Пока список пуст, применяется введённый срок и в отчёт уходит предупреждение — выдумывать чужой норматив модель не будет.

### Логика финансирования

- платежи до открытия ПФ — БРИДЖ или собственный капитал;
- платежи после открытия ПФ — ПФ, но только если ВРИ включена в банковский бюджет;
- если банк ВРИ не финансирует, платёж остаётся на капитале и **исключается из базы долгового финансирования**: он не создаёт ни выборки БРИДЖа, ни выборки ПФ;
- при заданных долях доля ПФ до его открытия принимается БРИДЖем, а без банковского бюджета — капиталом;
- проценты по рассрочке считаются отдельной статьёй `vri_interest` и не смешиваются с процентами по кредитам.

### Очерёдность

ВРИ — обязательство всего проекта, а не отдельной очереди. Даты платежей у всех очередей одни и те же, различается только доля: шестилетняя московская рассрочка идёт по общему календарю и не растягивается на срок проекта вслед за стартом каждой очереди. Ранние очереди платят из ПФ, поздние ту же дату несут БРИДЖем, потому что их ПФ ещё не открыт. Платёж, приходящийся на период до старта очереди, относится на её первый месяц — с явным предупреждением.

Сводный блок собирается в `vri` бандла очерёдности: одна сумма обязательства, общий график и разбивка каждого платежа по очередям.

### Что видно в отчётах

Карточка «Плата за изменение ВРИ» в отчёте: сумма обязательства, основной долг, проценты по рассрочке, расходы на обеспечение, выплаты до и после открытия ПФ, суммы в БРИДЖе, ПФ и капитале, график с остатком на каждую дату и источником платежа.

В выгрузке модели появился лист **«ВРИ»** — итоги, условия и график с формулами; он есть и в файле каждой очереди, и в книге-консолидаторе. В структуру расходов добавлена строка «Проценты по рассрочке ВРИ».

### Шаблон ПЛАТО не трогаем

Шаблон принимает плату за ВРИ одной суммой на листе «Расчет ВРИ (ТЭП)» и рассрочку выразить не может. Менять сам шаблон не стали: в архив выгрузки добавлена отдельная книга **«ВРИ_график_….xlsx»** с итогами, условиями и графиком платежей. Шаблон остаётся ровно тем файлом, что и был, а детализация едет рядом. Если изменения ВРИ не требуется, книга в архив не кладётся.

Версия приложения, `/health`, заголовок страницы, User-Agent и версия бота обновлены до `0.12.47`.

# DevelopAid v0.12.46 — социальная нагрузка раскладывается по очередям сама

## Что изменено в v0.12.46

Раньше при включённой очерёдности социальные объекты расставлялись заглушкой: ДОУ — в первую очередь, школа и поликлиника — во вторую, независимо от размера очередей. Первая очередь и так несёт сети, подготовительный период и самый длинный срок, поэтому заглушка систематически перегружала самое тяжёлое место проекта.

Теперь работает **поздняя раскладка**: объекты уезжают вправо настолько, насколько позволяют ограничения.

| Очередей | ДОУ | Поликлиника | СОШ |
| --- | --- | --- | --- |
| 2 | 2 | 2 | 2 |
| 3 | 2 | 2 | 3 |
| 4 | 2 | 3 | 4 |
| 5 | 2 | 4 | 5 |

- **первая очередь по умолчанию без социальных объектов**;
- школа всегда в последней очереди — она самая дорогая и самая долгая;
- ДОУ во второй: дошкольники появляются с первым заселением;
- поликлиника ближе к концу, но именно ей первая очередь разрешена, если туда двигает обязательство.

### Обязательства сильнее автоматики

Потребность может существовать и без проекта — из-за дефицита мест в округе. Это внешний факт, из ТЭП он не выводится, поэтому у каждого объекта появился параметр «требуется не позже очереди N»: `kindergarten_not_later_than`, `school_not_later_than`, `clinic_not_later_than`. Если он задан и жёстче автоматики, объект переезжает раньше, а в раскладке видно почему.

Каждый объект отдаёт `reason` — «поздняя раскладка», «обязательство: не позже очереди N» или «вручную», — а также `auto_phase` (куда поставила бы автоматика) и признак `moved_earlier`. Видно и цену вопроса: перенос объекта на очередь вперёд сразу отражается в пике ПФ.

Ручная раскладка из реестра очерёдности по-прежнему главнее: если очередь у объекта проставлена руками, пересчёт её не перетирает.

### Что видно в отчётах

В сравнении очередей появились столбцы **«Социальная нагрузка, млн ₽»** и **«Социальные объекты»** — и в интерфейсе, и в листе «Сравнение очередей» книги-консолидатора. Сумма по столбцу считается формулой.

Режим денежной компенсации не затронут: там распределять нечего, платёж дробится по датам как раньше.

Значения `11% / 9% / 7%` больше не зашиты в выпадающий список. Названия сценариев автоматически подтягивают текущие целевые ориентиры из полей `Консервативная цель`, `Базовая цель` и `Оптимистичная цель`.

Например, после изменения базовой цели на `10,5%` интерфейс и отчёт показывают `Базовый → 10,5%`. Значения также синхронизированы с легендой графика.

## Изменения, сохранённые из v0.12.3

## Что исправлено

### 1. Отдельная налоговая маржа объектов КРТ

МФОЦ / офисы, ТЦ / ОСЗ и наземный паркинг теперь рассчитываются как самостоятельные продукты:

- МФОЦ и ОСЗ — реализованные м² × (фактическая цена месяца − себестоимость на продаваемый м²);
- наземный паркинг — реализованные машино-места × (фактическая цена места − себестоимость места);
- каждый объект включается в общую налоговую базу один раз.

### 2. Налог начисляется накопительно и помесячно

Логика приведена к Excel-эталону `PLATO_template(1).xlsx`:

1. суммируется маржа реализованных основных продуктов;
2. добавляются отдельные маржи объектов КРТ;
3. вычитаются выплаченные проценты и банковские комиссии;
4. налог 25% начисляется на накопленную положительную базу не ранее РВЭ;
5. ранее начисленный налог повторно не учитывается.

В ответе расчётного API появились:

- `finance.profit_tax_schedule`;
- `finance.tax_rows`;
- `finance.tax_margin_by_product`;
- `finance.tax_cost_by_product`;
- `cashflow.profit_tax`.

### 3. Исправлен горизонт отдельных объектов

Если строительство или продажи объекта КРТ заканчиваются позже жилой части, горизонт проекта автоматически продлевается до последнего денежного потока. Поздняя выручка теперь одновременно попадает в:

- финансирование;
- налоговый расчёт;
- NPV / IRR;
- проектный и акционерный cash flow.

### 4. Убран двойной учёт платы за лимит в NPV

Плата за лимит уже капитализируется в задолженность по процентам и входит в `interest_payment` при фактической выплате. В cash flow она больше не вычитается второй раз отдельной строкой.

### 5. Техническая синхронизация версии v0.12.3

В базовой сборке версия приложения, `/health`, заголовок страницы и User-Agent были приведены к `0.12.3`. Устаревшая версия `0.8.4` в `/health` удалена.

### 6. Платон Сергеевич видит новый налоговый блок

Для `explain_metric` и `trace_metric` добавлена метрика `profit_tax`: агент показывает маржу основных продуктов и КРТ, признанную себестоимость, расходы финансирования, формулу и помесячные платежи.
